## 2. 两条链路（同一端点，靠入图分流）

| | 文生 t2i | 图生 image_edit |
|---|---|---|
| 触发 | 请求体无 `image` | 至少一张入图 |
| `chat_type` / `sub_chat_type` / `extra.meta.subChatType` | `t2i` | `image_edit` |
| `messages[0].files` | `[]` | 每张入图一项（见 §4） |
| `extra.meta.size` | 有（比例枚举或 `auto`） | **无**（无实测依据，故不发） |
| 顶层 `size` | 有 | **无**（与上一行同一条规则） |
| 上游调用 | 1 次生成 | 1 次生成 + N 次上传 + 1 次建会话 |

三个 `chat_type` 字段必须一致 —— 前端 bundle 里三处都写，只发一处是猜。

## 3. 两个身份门

| | 登录态 `normal` | 访客态 `guest` |
|---|---|---|
| 身份 | `token` JWT（通道密钥或 jar 里的 `token=`） | 设备指纹：`bx-umidtoken` + `bx-ua`，**无** `token` |
| `Referer` | `/c/new-chat` | `/c/guest` |
| 额度 | 按账号 | 按设备身份，**默认模型实测 4 张/天**，**与出口 IP 无关** |
| `bx-ua` / `bx-umidtoken` | 可选 | **必需**（它们就是凭据） |

**通道密钥（`ctx.key`）有四种形态**，仅凭形状区分，一个脚本服务四类渠道：

| 密钥 | 门 | 行为 |
|---|---|---|
| `eyJ...`（JWT） | 登录 | 写进 Cookie 的 `token=`，jar 其余部分取自 `cookie` 选项 |
| `""`（空） | 由 jar 决定 | jar 自己的 `token=` 说了算；没有就访客 |
| `guest` | 访客 | jar 里若残留 `token=` 会被**删掉**（否则上游按 cookie 认证成账号） |
| 整串 cookie | 登录 | 这一串**就是** jar，原样发出，token 从中取 |
| `<user>｜<password>` | 登录 | `POST /v2/auths/signin` 换 JWT（见 §3.1） |

**实测进度（2026-09-19，均为真实出图 + 门归属核对）**：

| 形态 | 状态 | 证据 |
|---|---|---|
| `eyJ…`（JWT） | ✅ **已实测**（01:50，1 发） | 账号门；**0 次 signin**；`reports/2026-09-19_qwen-key-jwt/` |
| `<user>\|<password>` | ✅ **已实测**（01:43，1 发） | 账号门；1 次 signin（trace 有 `stage=auth`）；`reports/2026-09-19_qwen-account-pair-auth/` |
| `guest` | ✅ **已实测**（01:25，3 发） | 访客门；`reports/2026-09-19_qwen-guest-1k-modes/` |
| 整串 cookie（jar） | ✅ **已实测**（02:01，1 发） | 账号门；**0 次 signin**；用的是**真实预热 cookie + token** 的 304 字符 jar；`reports/2026-09-19_qwen-key-jar-empty/` |
| `""`（空密钥，凭据走 `X-Channel-Options.cookie`） | ✅ **已实测**（02:02，1 发） | 账号门；**0 次 signin**；jar 里没有 `token=` 时落访客门 ⇒ 缺 `bx_*` **发上游之前**即 400 `channel_config_error`（零额度，已实测） |

工具：`tools/qwen_key_form_smoke.py`（登录态三形态，一次 1 发、自带门归属核对）＋
`tools/qwen_guest_smoke.py`（访客门，三类形态链式）。

**访客身份轮换**：渠道配 `identity_url` 后，每次请求的 auth 相位向该地址取一份
`{"cookie","bx_ua","bx_umidtoken"}`（`tools/identity_service.py` 就是这样一个提供方）。**三者缺一即 502**：
只换一半不是轮换（umid 才是设备身份），继续烧旧身份的额度。

### 3.0 🔴 登录态也必须带**真实浏览器会话的整份 jar**（2026-09-18 真实链路实测）

用真实账号跑了一遍：`signin` 能拿到 209 字符 token，但只带 `token=<jwt>` 的 jar 打**生成端点**会被
x5sec 拒（`{"ret":["FAIL_SYS_USER_VALIDATE","RGV587_ERROR..."]}`）。⇒ 「票据」与「设备指纹」是两件东西：

| | 需要什么 |
|---|---|
| 登录（`signin`、t2t 流） | 只要 token（§2.5 variant D 的语境是 t2t 流） |
| **生成（本脚本的两条链路）** | token **＋** 浏览器指纹 jar（`ssxmod_itna` / `acw_tc` / …） |

脚本对这类响应会把原因写进报错（"发出的 jar 里除了 token 没有别的项"），因为一个裸 502 排查成本很高。
取得整份 jar 的可行路径：① 从真实浏览器导出（最快）；② 让 `identity_service` 在浏览器里
**把 token 种进 context** 再读回 jar（需要 Playwright）。

**精确到哪一步**（2026-09-18 8 账号实测的调用流水）：只带 token 时 `POST /v2/chats/new` 是 **200 通过**的，
被 x5sec 拒的是**生成调用** `POST /v2/chat/completions`。⇒ 建会话不看指纹，**出图才看**。

#### 🔴 2026-09-19 01:43 更正：**token-only jar 就能打生成端点**

用 pair 形态（渠道密钥 `<user>|<password>`，脚本自己 signin）真跑了一发，**结论与本节相反**：

| 观测 | 本次实测 |
|---|---|
| 发出去的 jar | **只有 `token=<jwt>`**（`_jar_for` → `_with_token(cookie="", jwt)`，且本次**没配** `cookie` 选项） |
| 预热拿到的 `acw_tc` 有没有跟着出去 | **没有** —— aiohttp 在**有显式 `Cookie` 头时不会合并会话 jar**（本地真 socket 实测：第二个请求线路上只有 `token=…`） |
| `POST /v2/chat/completions` | ✅ **200，12.2s 出图 1024×1024** |
| 归属 | 产物 `resource_user_id` **＝** 账号 JWT 的 `id`（`fbd31d55…`）⇒ **账号门**，不是 guest 回退 |

⇒ **「整份指纹 jar」不是生成端点的硬前提**。本节的"被 x5sec 拒"与 §6.3 的更正重叠（探针头不全 / 处于
x5sec 窗口），属**窗口态产物**，不能当作常态结论引用。
⚠️ 本节仍成立的那一半：**写接口要用 Cookie，`Authorization: Bearer` 不可用** —— 本形态正是把凭据
放进 Cookie 才通的。证据：`reports/2026-09-19_qwen-account-pair-auth/`（含门归属核对与 trace 摘录）。

### 3.1 多账号：L1 按账号分格，且登录必须**跨账号节流**（2026-09-18 实测）

`_SIGNIN_STATE` 是 `{sha256(pair): {jwt, ts, inflight}}`。单槽版本在多账号下会互相挤掉 token
（B 一登就把 A 挤掉 ⇒ 之后每个 A 请求都重新 `signin`）。

🔴 **实测教训（8 账号一轮）**：8 个账号在几秒内各登一次，**第 7、8 个账号拿到的是阿里 WAF 挑战页**
（200 + `text/html` + `aliyun_waf_aa`）—— 撞的是 signin 的 **IP 级频率墙**，不是账号问题。所以
"每账号一个冷却窗"不够，还需要**跨账号共用**的尝试间隔：`_SIGNIN_MIN_INTERVAL = 45s`
（按墙的 12 次/6 分钟反推，留余量），戳写进 L2（有 Redis 则全 worker 共用），被节流的请求走 guest 门。
**已签发的 token 不受墙影响**（同一批里 1–6 号账号第二轮的请求照常走到生成调用）—— 这条与 §2 的
"墙只拦新的 signin"一致。

⇒ 多账号的正确姿势：**要么 paced 冷启动**（每 45s 一个账号，8 个账号约 6 分钟铺满），
**要么预置 token**（一次 paced 的 provisioning 把各账号 JWT 写进共享缓存，运行时几乎不再登录）。

### 3.2 🔴 登录应该走**轮换出口**（2026-09-18 实测）

墙按出口 IP 算，而 token 是无状态 JWT（"墙只拦新的 signin"）⇒ **登录走轮换出口、出图走正常出口**
是正解，也顺带解决 3.1 的冷启动挤堆问题（每个账号各走不同 IP，几秒内可以登完）。

- 代理池 `pool.livetest.cn`：**2088 = 换连接即换 IP**（实测两次 → `38.6.213.199` / `38.6.213.200`），
  **2089 = 客户端级粘性**（口径"按域名"已被实测推翻）。凭据见 reverse-proxy 仓的
  `.workbuddy/memory/BASICS.md`。
- **实测救回**：被直连墙拒掉的两个账号，经 2088 立刻登录成功（无挑战页、token 209）⇒ 它们是**有效账号**，
  之前失败纯属出口问题。
- ⚠️ 实现障碍：该池**只吃 SOCKS5**（`http://` 形态 2088/2089 均失败），而 **aiohttp 没有原生 SOCKS**
  （只有 `proxy=` 的 HTTP 形态）。所以要么在工具侧用 SOCKS 登录（**token 服务**，与 `identity_url` 对称），
  要么加一个本地 SOCKS→HTTP 桥再让脚本用 `proxy=`；适配器镜像本身不宜引入 SOCKS 依赖。

**落地（2026-09-18，B 方案，已实跑）**：`tools/token_service.py` 持有账号、经代理池（每条连接换出口）
登录并把 token 发出来；渠道配 **`X-Channel-Options.token_url`**（如 `http://127.0.0.1:8792/token`）后，
脚本按 `?account=<email>` 取 `{"token": …}`，**完全不发 signin 与预热**。8 账号实测：

| 观察 | 结果 |
|---|---|
| 适配器侧 `signin` / 预热次数 | **0 / 0**（在链路上数的，不是"应该不会"） |
| 服务侧登录次数 | 第 1 轮 **8**（含此前被直连墙拒的两个账号）、第 2 轮 **0** |
| 两轮耗时 | 53.2 s → **5.2 s**（差的就是 8 次代理登录） |
| 生成额度 | 0 |

→ 多账号 + 轮换的正确形态：**一个账号一个渠道**（密钥 `<user>｜<password>`）+ 渠道 `token_url`；
脚本侧 `_SIGNIN_MIN_INTERVAL` 节流只在**脚本自己登**那条路生效（走服务时出口已轮换，卡 45 s 只会
让 8 个账号又排成 6 分钟的队）。

| 维度 | 要不要轮换 | 理由 |
|---|---|---|
| 访客身份（umid + cookie + bx-ua） | **要** | 单身份约 4~5 张/天，且与出口 IP 无关 ⇒ 只能换身份 |
| 登录态的设备指纹 | **不要** | 一个账号配一份稳定的真实浏览器 jar 反而更自然；频繁换指纹对同一账号是异常信号 |
| 登录态的账号（多账号） | 按额度需要 | 一个账号一个渠道（密钥形态 `<user>｜<password>` 即一条）；缓存已按账号分格，登录已跨账号节流 |

### 3.1 登录态 token 的取得与缓存

- `POST /v2/auths/signin`，体为 `{"email", "password": sha256(明文)}`（服务端收的就是哈希），
  **JWT 只在响应的 `Set-Cookie`** 里（body 是账号记录，没有 token）。
- 前置一次 `GET /auth` 预热，拿 WAF 冷启动 cookie。
- **该端点有 IP 级频率墙**：实测约 12 次/6 分钟即触发阿里云挑战页（**200 + text/html**），
  持续数分钟，**只有换出口才恢复**。故脚本带 `_SIGNIN_RETRY_COOLDOWN = 300s`：窗口内不重试。
- JWT 实测有效期 30 天，缓存 6 天（`_SIGNIN_TTL`）。
- **两层缓存**：L1 = 模块级 dict（热路径零 I/O）；L2 = `ctx.cache`（配 Redis 则跨 worker 共享，
  只在 L1 未命中时读一次）。失败也穿透写回一个冷却时间戳。401 自愈路径**跳过 L2 读**——
  缓存里那份就是刚被判死的 token。

## 4. 请求指纹、上传与响应

**头**：`Cookie` + `bx-v`/`bx-ua`/`bx-umidtoken` + `User-Agent`/`Origin`/`Referer`/`source=web`/
`version=0.2.0` + `Accept: application/json` + `Connection: keep-alive` + `X-Accel-Buffering: no` +
`Accept-Language` + `Timezone` + `X-Request-Id` + `Sec-Fetch-*` + `sec-ch-ua*`。
`version` 两模式都发（§5 冲突未定论，不据它删）；`Timezone`/`X-Request-Id` 每次调用现生成。

🔴 **后三条不是装饰**（2026-09-19 落地，依据参考仓 §10.19 与「写类请求必备头」附录）：
那边实测**同一账号、同一出口**下，缺 `Sec-Fetch-*`/`Timezone`/`Connection`/`X-Accel-Buffering`
（且 `Accept` 写成 `text/event-stream`）的一套头**必现 RGV587**；换成 `biz-api::build_headers`
那套头后**连续 3 次成功出图** —— 当天一整批关于限速、账号、出口 IP 的结论都因此被撤回。
本脚本**本来就发** §6.3 自证必需的那三个头（`bx-v`/`Timezone`/`X-Request-Id`）以及
`Sec-Fetch-*`，与 `build_headers` 的差集就是上面这三条（`Content-Type` 由 aiohttp 的
`json=` 自动带，2026-09-19 实测出线头确认，**不是**缺口）。
⇒ 处置口径：**见到 RGV587，第一步把本脚本的头集合与 `build_headers` 逐字段对齐**，
再谈限速、冷却、换号。
⚠️ 但这与「本仓现在能不能出图」是两件事，别互相套用：§6.3（2026-09-19 00:25–00:35 实测）
记录本仓 `GET /auth` / `chats/new` / `signin` **都通**，**只有生成端点** `completions` 仍回
x5sec —— 访客身份、脚本 signin、整份浏览器 jar **三条凭据路径都试过、都被拒**。补头解决的是
「读 / 建」那道门（已由本仓巡检工具自证），生成端点那道闸当时更像**按凭据/设备分桶的累计**，
处置是**等冷却**而非再补头。
✅ **01:12 复核：生成端点已恢复**。本仓随后用**新铸的访客身份**跑了三种形态 × 1K，
**6 发（有头 3 + 无头 3）全通、无一条 x5sec**（`reports/2026-09-19_qwen-guest-e2e/REPORT.md`）。
⇒ 「头集合对齐」与「真实出图」是**两条独立证据**，现在两条都有本仓自己的读数支持。

> ⚠️ 引擎默认还会把通道密钥发成 `Authorization: Bearer <key>`，而本上游**不认**它。
> 渠道应配 **`X-Auth-Emit: none`**；脚本自己也只在 Cookie 里放凭据，不自发 `Authorization`。

**上传（仅 image_edit）**：`POST /v2/files/getstsToken` → 取 STS 凭据 → `PutObject`（OSS V4 签名）
→ 把结果拼成 `messages[0].files[]` 的一项（`type/id/url/name/status=uploaded/file_type/showType`）。
单次 PUT 上限 2 MiB（字节超限**明确报错**，不静默截断）；不做 multipart。

🔴 **多张垫图并发物化**（2026-09-19 起）：N 张走 `ctx.fanout` —— 保序（`files[i]` 属于 `refs[i]`）、
并发上限 `fanout_concurrency`（现 5）、最早失败的异常**原样抛出**（超 2 MiB 的明确拒绝不会被塌成 502）。
`docs/07` §14.2.1 允许并发**素材物化**（排除的只是并发生成调用）；此前 qwen 是四渠道里唯一没做的一档
（`openai`/`google`/`volcengine_ark` 早就做了）。单张时走串行路径，**行为逐字节不变**。
⚠️ 两处副作用要知道：① **PUT 的到达顺序不再确定** —— 契约是 `files[]` 的顺序、从来不是"到达顺序"，
本仓两个集成用例的断序方式据此改成「把 `files[i]` 回链到它上传的字节」（更严：同时钉住"没换图"）；

## 5. 尺寸（`size`）

上游真枚举是 **5 个比例**：`1:1` / `16:9` / `9:16` / `4:3` / `3:4`，外加 `auto`
（**`auto ≠ 1:1`**：实测 pro 档会出 2528×1696）。脚本按 `RATIO_TO_HW` 知道每个比例的规范分辨率。

档位不是 size：`1K→qwen-image-3.0`、`2K/4K→qwen-image-3.0-pro`，且 **上游没有 4K 档**
（bundle 里 `4k` 只出现在示例提示词文本里、`3840` 零出现、最大边常量 2688）。

**方言的识别与归一化在框架里**：`ctx.parse_size(raw, ratios=…, tiers=…, resolutions=…)`
（见 `docs/07` §5.1 与 `docs/04` AC-35）；本脚本只保留**厂商策略**：出线用比例枚举、
非规范分辨率原样透传、档位改 model、认不出回 `auto`。

### 5.1 🔴 实测：分辨率由**模型**决定，`size` 抬不动（2026-09-18 反向代理实测）

| 用法 | 实测输出 |
|---|---|
| t2i（默认 / `2.0-pro` / `3.0-pro`） | **2048×2048** |
| i2i（单图 / 多图，含 20 张输入） | **1024×1024** |
| t2i + `size="16:9"` | **仍 2048×2048** ⇒ 比例**未被上游采纳** |

显式像素是唯一可能强推更大的路径，实测结论**是负面的**：

| 请求 | 实得 | 判定 |
|---|---|---|
| `qwen-image-3.0-pro` + `size="3840*2160"` | `internal_error`，**挂满 300s** | 🔴 **挂死**（不是降级） |
| `qwen-image-3.0-pro` + `size="2688*1536"`（前端最大边） | `internal_error`，挂满 300s | 🔴 挂死 |
| `qwen-image-3.0` + `size="3840*2160"` | 2048×2048 | ⚠️ 显式像素被**静默忽略** |

⇒ 前端那个「最大边 2688」是 UI 的比例→像素预设，**上游 pro 模型不接受该像素请求**。

🔴 **本仓护栏（2026-09-18 落地）**：`-pro` 模型（`image_model` 以 `-pro` 结尾）**且** size 是
**非表内像素对**（`ctx.parse_size` 判为 `resolution` 而没有对应比例）时，脚本改发 **`auto`**，
并在 trace 上留一条 `size_guard`（`requested` / `sent` / `size_hw`）。
理由：这条请求在该模型上**必然失败**，而 `auto` 是能跑通的请求 —— 与脚本「认不出就回 auto、绝不因 size
报 400」的既有取向同一条；**丢弃的值进 trace，不静默吞掉**。比例枚举与表内分辨率（会被换算成比例）
都不受影响，非 pro 模型行为不变。

其余两条实测，用于对齐预期而不是改契约：

- **档位不是提速手段**：默认模型 31.7s vs `qwen-image-3.0`（1K 映射到的模型）31.2s，
  差异在噪声内。真正的耗时差异在模型上（`3.0-pro` ≈ 52–57s，约为默认的 1.7 倍）。
- **多图不拖慢生成**：i2i 从 3 张到 20 张，耗时均 29.1–29.4s ⇒ 多图成本只是「多传几个文件」。

#### 🔴 本仓自己的实测：**1K 档经 `extra.meta.model` 真的生效**（2026-09-19 01:26，访客门）

上表全部来自参考仓，改的是 `size` 字段；本脚本改的是 **`extra.meta.model`**（档位表 `TIER_TO_MODEL`）。
两条路在访客门 × 1K × 三类形态上各跑一发，产物实测（`reports/2026-09-19_qwen-guest-1k-modes/`）：

| 用例 | 耗时 | 产物 | 尺寸 |
|---|---|---|---|
| t2i | 10.8s | 1.37MB PNG | **1024×1024** |
| i2i | 17.7s | 1.36MB PNG | **1024×1024** |
| multi（2 张输入） | 24.9s | 1.29MB PNG | **1024×1024** |

⇒ 与参考仓「`size="1K"` 不生效、一律 2048²」**不矛盾**：那边把 `1K` 当 size 发（上游忽略），
本脚本把它映射成模型 ⇒ **`1K`（1024²）与 `2K` 的分辨率差第一次被本仓实测到**。

#### 🔴 2K 档实测（2026-09-19 01:57，jwt 形态）：**不是固定 2048²**

2K 档＝`extra.meta.model=qwen-image-3.0-pro` + `size="auto"`，而 **`auto` 的尺寸由模型按提示词决定**。本仓那发（戴围巾的柴犬）产出 **1792×2400**（`output_image_type=qima_output_2k`，竖构图）；

⇒ **「2K 就是 2048²」是错的**；要固定形状只能发比例枚举（而比例**也可能不被采纳**，见上）。
⏱️ 2K 那发耗时 **≈70–80s**（客户端未计时，由任务时长与会话 `updated_at` 夹出），比 1K 的 13.3s 明显更慢。
🔴 另：`extra.output_image_hw` 现在有**两例非方形样本都是 `[高, 宽]`**（`[[1696,2528]]`↔2528×1696、`[[2400,1792]]`↔1792×2400），但脚本仍**不替上游裁决**、原样进 trace。

## 6. 失败形态与归因

无图响应分四类（`_diagnose`，各有不同的责任人）：

| 形态 | 含义 |
|---|---|
| WAF 挑战页（HTML + `aliyun_waf`） | 反爬头/凭据需重抓，**不是** IP 被封 |
| `RGV587` / `FAIL_SYS_USER_VALIDATE` | x5sec 突发，**命中后不要连发**（见 §6.1） |
| 空 SSE（0 条 data 行） | 疑似网关/风控拦截 |
| 有 SSE 但无 URL | 疑似生成被中断；**也可能是额度耗尽**（3.0-pro 的流内 `error` 帧，见 §6.0） |

### 6.0 额度耗尽有两种投递方式，且两个 `code` 都是**过载的**（2026-09-18 实测）

**投递方式**（同一件事的两种形态，判据必须同时覆盖 `data.code` 与 `error.code`）：

| 模型 | 额度耗尽时 |
|---|---|
| 默认模型 / `qwen-image-2.0-pro` | JSON 拒绝：`data.code = RateLimited` + `details =「今日生图额度已用完…」` |
| **`qwen-image-3.0-pro`** | 流内 error 帧：`{"error": {"code": "quota_limit", "detail": …}}`，约 1.5s 结束、无图 URL |

**`code` 不足以定语义** —— `RateLimited` 与 `quota_limit` **各自**都承载着两种拒绝：

| `details` 文案 | 含义 | 该怎么做 |
|---|---|---|
| 「今日生图额度已用完，登录后可继续生图。」 | **日额度**（该身份该周期作废） | 切身份；**不要重试同一条** |
| 「目前服务访问量较大，请稍后再试。」 | **瞬时过载**（与并发/负载有关，**单发串行、全新身份也会命中**） | **稍后重试**；别切身份、别标周期耗尽 |

⇒ 本脚本按**文案**判定：只有实测的日额度文案映射 **429 `upstream_quota_exhausted`**（不重试），
其余走 **502 `upstream_error`**（可重试）并在消息里写明"不是该身份当日额度耗尽"。
🔴 **2026-09-19 补第二处：静默丢弃 ⇒ 500**。上游有时**200 回来却什么都不说**：0 条 `data` 行
（或响应体完全为空），且**会话里连消息都没登记**（实测伴随 ~0.2s 返回；见
`reports/2026-09-19_qwen-stale-fileid/` 的第一发）。这种形状现在给 **500 `server_error`**
（`code=upstream_error`）而不是 502 —— 依据是 `ctx.fail` 的约定与 `docs/06` 的同一用法：
**状态码就是给下游的重试信号**（4xx＝别重试、5xx＝可重试）⇒ 让 **new-api 自己重试一次**。
守卫（都钉了单测）：**有 SSE 帧但无图**（生成被中断）与 **WAF 挑战页**保持 502（重试无用）。
🔴 **2026-09-19 补第三处：内容审核未通过 ⇒ 400 `content_filter`**（与上面那条**方向相反**）。
**实测帧（上游原文，2026-09-19）**：

```
data: {"error": {"code": "data_inspection_failed", "modality": ["text"], "stage": "input",
                 "details": "内容安全警告：输入数据可能包含不适当的内容！"},
       "response_id": "a900b4c7-…", "response_index": 0}
```

⇒ 字段勘误：标志在 **`error.code`**（bundle 里读到的 `error_code` 是另一拼法 ⇒ **两种都认**，
实测以 `code` 为准）；另带 `modality`（被拒的模态：text/image）与 `stage`（拒在**输入**还是输出）
—— 这两项决定了给调用方的建议（"改提示词" vs "换素材"），所以进 trace。
文案兜底**不在本脚本里了**（AC-36）：自然语言词表属**跨渠道共享**，落在
`script_store/capabilities/_shared.json` 的 `moderation_wordings`（改数据不发版，本渠道只剩**厂商专属 code**
`CONTENT_CODES`）；判定与出口都由框架件 `ctx.matched_moderation` / `ctx.fail_moderation` 收口，
所以三个渠道对客户端的说法一致（400 `content_filter` + `param=prompt` + 统一后缀）。
**trace note 自证**：命中时记 `outcome="content_refused"` + `error_code` + `modality` + `refused_at` + `details(前 120 字)`
⇒ 生产里**第一次真实出现**就留档，不必再为了拿证据去构造违规请求。
这一类**同 prompt 重试必再被拒**，
报 5xx 只会让 new-api 白烧一次生成、还告诉调用方"稍后能成"。故给 **400**
（`code=content_filter`、`param=prompt`、消息写明"改提示词或换素材"）。
⇒ 三条并排看：**静默丢弃＝500（可重试）／有帧无图与 WAF 页＝502／审核拒答＝400（别重试）** ——
判据始终是同一句话：**状态码就是给下游的重试信号**。
🔴 **2026-09-19 补上一维：文案判定还要看「哪一跳」**（`_fail_qwen_error(..., hop=)`）。
**上传跳（`getstsToken`）不计费** ⇒ 它上面出现的任何"额度"措辞都不可能是「生图额度耗尽」，
一律按瞬态处理（消息写明"上传不计费 ⇒ 与生图额度无关"）。否则一次大 N 多图的**上传频控**
会被读成"该身份当日额度耗尽"，按本仓口径等于**把一条好身份停用一天**。
（实测那一步的限流按**身份**计窗：账号 20 次/窗口、访客 5 次/窗口，换出口无效。）
判反的代价不对称：多打一次很快失败的请求 vs **白损失一条身份的整天额度**（参考仓按 `code`
判过，实测踩中）。⚠️ 也不要靠 `entitlement_quota.times_left` 当熔断依据 —— 它出图后不减（§7）。

### 6.1 🔴 x5sec 突发的归因与处置（2026-09-18 实测）

被拦时的响应是 `{"ret":["FAIL_SYS_USER_VALIDATE","RGV587_ERROR::SM::…"],
"data":{"url":"…/_____tmd_____/punish?x5secdata=…"}}`（`chats/new` 仍然 200，**被拒的是生成调用**）。

**同一拒绝有第二种投递方式**：`code` 里带 `FAIL_SYS_USER_VALIDATE` / `RGV587` ——
参考仓 `biz-api::_stream_images` 正是按 `code` 判的（`qwen-chat-api.md` §6 把两种形态并列）。
本脚本**两种形态都认**（2026-09-19 补），并落进同一个退避窗：只认 `ret` 的话，`code` 形态会
落进通用 502 且**不记窗** ⇒ 下一发立刻又打上游，而「命中后连发只会加深」正是参考仓的结论。

**排除法实测（同一份 2419 字符的完整浏览器 jar）**：

| 变量 | 结果 | 判定 |
|---|---|---|
| 出口：本机直连 vs 代理池 2088 | **两者都拒** | ❌ 出口不是变量（参考仓也推翻过"出口是根因"） |
| 凭据：整份 jar（含 `ssxmod_itna`/`tfstk`/`isg`/`cna`/`atpsida`/`token`） | 仍被拒 ⇒ **不是"缺指纹"** | ❌ 指纹不是变量 |
| `version: 0.2.0` 头 | 脚本一直都在发；同账号在同仓记录里带该头**曾 200 成功** | ✅ 已满足 |
| **短时高频写请求** | 当天 30 分钟内对该账号做了 20+ 次写请求（8 账号两轮 + 对照实验 + 三条形态） | ✅ **最可能的触发器**（与参考仓 R-2 一致） |

⇒ 处置是**等**，不是补更多头：命中即记一个**按账号**的退避窗（`_X5SEC_COOLDOWN = 120s`），
窗内直接失败并把"还有多少秒 / 重试无用"写进报错，**不再打上游**（连发只会加深）。
⚠️ 响应里的 `punish` 链接是**验证码页**：本仓**不做任何绕过尝试**（与参考仓同一条红线）。
⚠️ 该窗口记在 L1（本进程）；要多 worker 共担，把它挪进 `ctx.cache` 即可。

  ①部署机上 `headful` 需要显示服务（Xvfb / GUI 会话），而 **SSH-only 的服务器上它会直接起不来**——
  这条与"指纹好不好"无关，是能不能跑的问题；②池子默认 4 个并发浏览器，无头在内核/内存上都更省；
  ③实测**两者无可观测差异**：有头 3 发 / 无头 3 发产物与耗时一致（t2i 10.9 vs 11.2s、i2i 16.8 vs 17.5s、
  multi 25.2 vs 24.9s），无头铸的身份打免费 `chats/new` 同样 200 + chat id；
  ④参考仓的判据（§2.9）是**站点与指纹 SDK 都不读 `navigator.webdriver`**（静态搜性已校准），
  20 条 playwright 身份 20/20 通过并真实出图 ⇒ 没有"必须更像真人"的证据。
  ⚠️ **有头是"诊断档"而不是"生产档"**：真的开始铸不出身份（umid 空 / bx_ua 缺失 / 身份被拒）时，
  第一件事是**在出问题的那台机上**用 `--headful` 跑一次做差分，而不是把生产改成有头。
  ⚠️ **别把两个旋钮混为一谈**：headless≠反检测。无头下真实 UA 是 `HeadlessChrome/153…`，
  但铸造器与参考仓都在 **context 层显式写 UA**（`new_context(user_agent=…)`）⇒ JS 可见层面被掩盖；
  「UA 报 152 / 引擎是 153」这个**版本错配**在两种模式下**同样存在**，要修得整仓一起改（参考仓 §2.9）。
- 登录渠道的 `X-Auth-Emit: none` —— **这不只是"贴合抓包"**：实测**只发 `Authorization: Bearer`
  的凭据在没有写接口处可用**（`chats/new` 通、`chat/completions` 落 x5sec 惩罚流，
  同 token 同头只换凭据形态即复现），即漏配 `none` 会把渠道推进风控。
  `<user>|<password>` 形态要预期**首次请求有一次 signin**。
- 401 自愈依赖"重建 body 与第一发不同"（chat_id 会重新铸造）—— 别把建会话改成幂等。
