# OpenAI Images 适配微服务 — 整体解决方案

## 1. 项目概述

### 1.1 背景与目标

构建一个 **OpenAI 协议兼容网关（Adapter）**，将任意上游图像/多模态服务（同构或异构）统一转换为 OpenAI 标准格式，对外暴露三个核心端点：

| 端点 | 能力 | 说明 |
|------|------|------|
| `POST /v1/chat/completions` | 多模态对话（文本 + Vision） | 支持图像输入、图像理解、图文混合输出 |
| `POST /v1/responses` | Agent 工作流 + 工具调用 | 支持 `image_generation` 工具、状态链、上下文压缩 |
| `POST /v1/images` | 专用图像生成 | 文生图、图生图，统一输出 `url` / `b64_json` |

### 1.2 核心价值

- **协议统一**：客户端只需对接一套 OpenAI SDK，即可调用任意异构上游
- **同构代理**：OpenAI/Azure 等原生兼容上游直接透传，零损耗转发
- **异构转换**：国产文生图、Stable Diffusion、Midjourney 等通过 Python 脚本灵活映射
- **可观测**：全链路基于 Logfire（OpenTelemetry）实现分布式追踪、性能监控、错误归因

## 2. 问题定义

### 2.1 同构上游（OpenAI / Azure / Claude 兼容）

| 痛点 | 说明 |
|------|------|
| 多 Key 管理 | 不同团队/项目使用不同 API Key，需统一管控 |
| 多区域路由 | 不同地区延迟差异大，需智能调度 |
| 用量管控 | 缺乏配额、限流、审计能力 |

**解决策略**：New API 现有能力已覆盖，Adapter 作为标准下游渠道透传。

### 2.2 异构上游（国产模型、SD、MJ 等）

| 痛点 | 说明 |
|------|------|
| 协议差异 | 上游使用自定义 JSON 结构，与 OpenAI `messages` / `prompt` 完全不兼容 |
| 字段映射 | `size=1024x1024` 需映射为上游的 `resolution=1:1` 或 `width=1024&height=1024` |
| 认证差异 | 部分上游使用 AK/SK 签名、临时 Token，非标准 Bearer |
| 异步模式 | Midjourney 等返回 Job ID，需轮询获取结果 |
| 输出格式 | 上游返回 URL / 二进制 / 存储 ID，需统一为 OpenAI 的 `url` 或 `b64_json` |
| 多模态输入 | Vision 场景的 `image_url` 需下载、转码、按上游要求重组 |
| 工具缺失 | 异构上游无 `image_generation` 工具概念，需网关层模拟编排 |

**解决策略**：Python 脚本映射引擎，每个上游独立脚本，动态加载、热更新、沙箱执行。

## 3. 核心设计原则

### 3.1 分层解耦

```
客户端 ──► New API（流量治理：鉴权/计费/路由）
              │
              ├──► 同构上游 ──► 直接转发
              │
              └──► Adapter（协议转换：映射/编排/格式化）
                        │
                        ├──► 异构上游 A（国产文生图）
                        ├──► 异构上游 B（国产多模态）
                        └──► 异构上游 C（SD / MJ）
```

### 3.2 脚本驱动

- 每个异构上游对应一份 Python 脚本，以 `X-Script-Ref` 命名引用（如 `volcengine_ark/images@v1`）
- 脚本只有**一个入口**：`async def transform(ctx, payload, phase)`，用 `phase`
  区分职责（`auth` / `request` / `response` / `poll_request` / `poll_response`），
  而非多个具名钩子
- 脚本通过 `ctx` 对象访问基础设施（HTTP、Redis、对象存储、Logfire、图像门面），禁止直接系统调用
- 脚本以源码 sha256 为键缓存，改动即换键生效，无需重启服务

### 3.3 级联可编排（v1.1）

单次「一进一出」的协议转换无法覆盖「前处理 + 生图 + 后处理」「生图 + 超分」这类多级链路。做法是**复用既有 `transform` 单一入口**，不引入第二套执行路径：

| 机制 | 形态 | 作用 |
|------|------|------|
| `STAGES` | 脚本模块级声明，如 `STAGES = ["preprocess", "generate", "upscale"]` | 声明本上游需要几级，引擎按序驱动 |
| `phase` 分发 | 引擎以 `phase="request:{stage}"` / `"response:{stage}"` 回调同一个 `transform` | 一个函数内用 `match phase` 分支，无需多套钩子 |
| `ctx.stage` / `ctx.emit()` | 级间产物读写 | 上一级产出直接作为下一级入参 |
| `ctx.SKIP` / `STAGE_FALLBACK` | 整级跳过 / 失败降级 | 文生图跳过前处理；超分挂了返回原图并标 `degraded` |

**对既有脚本零影响**——未声明 `STAGES` 的脚本走的仍是原有单级调用链路，行为完全不变。

### 3.4 可观测优先

- 基于 Logfire（OpenTelemetry）实现全链路追踪
- 每个请求生成独立 Trace，包含：路由解析、脚本加载、请求转换、上游调用、响应转换、图片处理
- 级联请求在 `adapt` Trace 下额外产生逐级 `stage` Span（含 stage 名、剩余预算、耗时、degraded/skipped 属性），可直接定位是哪一级慢、哪一级降级
- 错误自动关联到具体脚本和上游，快速定位根因

## 4. 三端点适配策略

### 4.1 /v1/chat/completions

**路由是前门，不是脚本。** `/v1/images/generations` 是唯一规范格式，本路由只做两个方向的形态改写
（`adapter/api/frontdoor.py`），改写完以规范端点名进管道 —— 脚本永远不知道自己从哪个入口来。

| 场景 | 策略 |
|------|------|
| 纯文本对话 | **路由层**把 `messages` 按 role 折成规范 `prompt`（`system` / `developer` 作文本前缀）；脚本只读规范体 |
| Vision 输入 | 同上：`content` 数组里的 `image_url` 折入规范 `image`，**不解码、不下载**（三态透传，交给上游 URL 还是内联由脚本决定） |
| 图像输出 | 规范响应的 `data[]` 由**路由层**封装成 `content` 数组（`type: image_url`；`b64_json` 转 data URI） |
| 流式输出 | 上游非流式 → SSE 桥拆 chunk：文本按 8 字符切，图片整块一个 delta（图片切不开） |
| 多轮 | **截断到最后一条 user 轮**：文本与图片都只取最后一条，`assistant` 轮忽略。规范契约只有一个 `prompt` / 一个 `image`，历史无处承载。未知 `role`（如拼错的 `usre`）仍 400 `unsupported_parameter` |

### 4.2 /v1/images

| 场景 | 策略 |
|------|------|
| 字段映射 | `prompt` → 上游字段；`size` → 查表/计算 `width/height`；`quality` → `steps/cfg_scale` |
| 批量生成 | `n > 1` 时，若上游不支持批量，脚本内部循环调用 `n` 次后聚合 |
| 异步上游 | 上游返回 Job ID → 脚本用 `poll_request` / `poll_response` 两相位决定何时完成（引擎驱动轮询循环，见技术架构 §3.7） |
| 输出统一 | 上游 URL → 下载 → Base64；上游二进制 → 编码；统一封装为 OpenAI `data` 数组 |
| 级联生成 | 声明 `STAGES` 的脚本走多级链路：前处理（缩放/裁剪/蒙版）→ 生图 → 后处理（超分/转码/压缩）；后处理级失败按 `STAGE_FALLBACK` 降级返回上一级产物 |

### 4.3 /v1/responses（最复杂）

| 特性 | 策略 |
|------|------|
| `input` 转换 | 脚本将 `input`（string/array）转换为 `messages` 或上游专有格式 |
| `image_generation` 工具 | 脚本内部编排：调文本模型生成优化 prompt → 调文生图模型 → 组装 `output` 数组 |
| `previous_response_id` | 脚本通过 `ctx.cache` 查询历史上下文，拼接到当前请求；新结果写入缓存 |
| `reasoning` | 上游 thinking 内容映射到 `output` 中的 `reasoning` 类型 |
| 流式 | 脚本 `transform_stream_chunk` 将上游流式格式转为 OpenAI SSE chunk |

> **2026-09-11 注**：上表的 `input` 折叠、`previous_response_id` 状态链、`output` 组装已由
> **路由层前门**承担（`api/responses.py` + `api/frontdoor.py`），脚本只实现规范契约、不碰 `input`；
> 其中 `reasoning` 与脚本侧流式转换仍未实施。
> 多轮历史按**"轮"**截断到最后一条 user 轮（连续裸 part 属同一轮，`assistant` 忽略，未知 `role` 400）。
> 权威描述见 `docs/09` §7 / §7.1。

## 5. 部署方案

### 5.1 部署形态

| 环境 | 方式 | 说明 |
|------|------|------|
| 开发 | `docker-compose up` | 单节点，脚本卷挂载热更新 |
| 测试 | Docker Compose + CI | 自动化测试脚本映射正确性 |
| 生产 | Docker Compose / K8s | 多 Worker 进程，Nginx 负载均衡 |

### 5.2 服务清单

| 服务 | 角色 | 持久化 |
|------|------|--------|
| Adapter | 协议转换网关 | 无状态，脚本通过卷挂载 |
| Redis | 状态缓存、Job 锁、response_id 映射 | 可选 AOF |
| 对象存储（minio 后端） | 临时图片对象存储 | **无自动清理**：`TEMP_IMAGE_TTL` 只控制预签名有效期，对象删除属桶生命周期规则，代码不管（2026-09-11 定调不做失效期管理）；fal 后端则无此概念 |

### 5.3 资源规划

| 组件 | CPU | 内存 | 说明 |
|------|-----|------|------|
| Adapter | 2 核 | 1 GB | 4 Worker 进程，IO 密集型 |
| Redis | 0.5 核 | 512 MB | 纯缓存，可降配 |
| MinIO | 0.5 核 | 512 MB | 临时存储，可降配 |

## 6. 安全设计

| 层级 | 措施 |
|------|------|
| 脚本 AST 扫描 | 加载前解析 AST，禁止 `exec` / `eval` / `subprocess` / `__import__` |
| Import 白名单 | 仅允许标准库（`json`, `re`, `base64`, `datetime`）+ `ctx` 注入；图像处理经 `ctx.image` 门面，Pillow 不进白名单 |
| 运行时隔离 | 分层预算：纯转换钩子 30s、级联单级 120s、级联总预算 300s（上限 600s），超时报错 |
| 网络审计 | 所有 HTTP 通过 `ctx.http`，base_url 与凭证由 channel 头单值注入，Gateway 记录完整 URL + 耗时 + 状态码 |
| 级联约束 | 级联仅在单一上游内串联多级；跨上游编排不在范围内，避免凭证跨域 |
| 容器隔离 | 无特权、只读挂载、资源限制、非 root 用户 |

## 7. 关键指标（SLI）

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 端到端延迟（P99） | < 5s（文生图）/ < 500ms（纯文本） | 不含上游生图耗时 |
| 协议转换耗时（P99） | < 50ms | 脚本执行 + JSON 重组 |
| 管线调度开销（P99） | < 30ms | 不含上游调用与图像算子的纯编排开销 |
| 级联降级率 | < 1% | 后处理步骤失败触发 fallback 的比例 |
| 可用性 | 99.9% | Gateway 层无单点 |
| 错误归因时间 | < 2min | 通过 Logfire Trace 快速定位（级联可精确到步骤） |
| 脚本热更新延迟 | < 5s | 文件变更到生效 |
