# OpenAI Images 适配微服务 — 技术架构

## 1. 技术选型

| 层级           | 组件       | 选型                          | 理由                                       |
| ------------ | -------- | --------------------------- | ---------------------------------------- |
| **Web 框架**   | HTTP 服务  | `FastAPI` (基于 Starlette)   | 轻量 ASGI；用 `Header()` 把 11 个渠道头变成代码，/docs 可试调 |
| **ASGI 服务器** | 生产服务器    | `uvicorn` + `gunicorn`      | 多 Worker 进程绕过 GIL，单 Worker 内 asyncio 高并发 |
| **HTTP 客户端** | 上游调用     | `aiohttp`                   | 异步、连接池、流式下载、超时精细控制                       |
| **图片处理**     | 编解码/格式转换 | `Pillow` (PIL)              | 成熟稳定，支持常见格式转换和缩略图                        |
| **对象存储**     | 临时图片存储   | 端口 `adapter/storage`，后端可选 `MinIO`(S3 兼容) / `fal` CDN | 后端协议不同（minio 预签名会过期；fal 公网长期、异步 SDK），故抽成端口：`STORAGE_BACKEND` 选一个，新增 OSS/COS/TOS 只需加一个 builder，不动脚本与引擎 |
| **缓存/状态**    | 分布式状态    | `Redis` (aioredis)          | 异步客户端、支持 Hash/Expire、分布式锁                |
| **可观测**      | 全链路追踪    | `Logfire` (Pydantic)        | OTel 标准；`instrument_fastapi` 埋点，默认不采集 header |
| **配置管理**     | 配置加载     | `Pydantic Settings`         | 类型安全、环境变量自动映射、验证                         |
| **脚本热重载**    | 文件监听     | `watchdog`                  | 跨平台、低延迟、资源占用低                            |
| **序列化**      | JSON 处理  | 原生 `json` + `orjson` (可选)   | 标准库足够，orjson 用于极致性能场景                    |
| **容器化**      | 部署       | `Docker` + `Docker Compose` | 单文件编排、开发/生产一致、脚本卷挂载热更新                   |

## 3. 组件详细设计

### 3.1 HTTP 接入层 (`adapter/main.py`)

```python
# 端点注册：渠道契约用 Header() 声明，缺失时由 channel.py 报 channel_config_error
app = FastAPI(title="Image Adapter", lifespan=lifespan, middleware=middleware)

app.add_api_route("/health", health_handler, methods=["GET"])
for path, handler in (
    ("/v1/chat/completions", chat_handler),
    ("/v1/responses", responses_handler),
    ("/v1/images/generations", images_handler),
    ("/v1/images/edits", image_edits_handler),
):
    app.add_api_route(
        path, handler, methods=["POST"], dependencies=[Depends(channel_contract)]
    )

# 中间件栈（全部为纯 ASGI；BaseHTTPMiddleware 每请求约 +0.4ms，见 §4）
middleware = [
    CORSMiddleware,       # 跨域，含渠道头预检白名单
    LoggingMiddleware,    # request_id 注入 + 访问日志
    RateLimitMiddleware,  # Redis 滑动窗口；Redis 不可达时降级为进程内计数
]

# 错误出口集中注册：404/405/422 与未捕获异常统一为 OpenAI 错误体
install_error_handlers(app)
```

**流式输出支持**：

- 非流式：直接返回 JSON Response
- 流式（SSE）：使用 `StreamingResponse`，yield `data: {...}\n\n` 格式
- 上游非流式但客户端要求 SSE：Gateway 层将完整响应拆分为多个 chunk 推送


### 3.2 核心调度器 (`adapter/api/pipeline.py`)

> 无 `adapter/router.py`。本服务不按 model 路由——**渠道、上游 URL、脚本、凭证
> 全部由控制面（New API）随请求以 header 传入**，所以没有注册表查询这一步。
> 编排收敛在各端点共用的 `api/pipeline.py::adapt()` 里。

**实际调度流程**（`adapt()`）：

```
接收请求
    │
    ├──► check_admission()          # X-Adapter-Key 比对（hmac.compare_digest）
    │
    ├──► parse_json_body / prepare  # 端点自带的载荷校验与规范化
    │
    ├──► parse_channel(headers)     # X-Upstream-Url / X-Script* / X-Stages
    │                               # → ChannelSpec，含 SSRF 校验
    │
    ├──► resolve_source(spec, store)     # 来源策略：尺寸/sha256 钉死/白名单
    │     └─ ChainStore: overlay → image # 查找（§3.5.2）
    │
    ├──► script_cache.load(source)  # 按源码 sha256 命中；未命中则 AST 扫描 + 编译
    │
    ├──► 装配 AdapterContext        # 复用 lifespan 建好的 http / asset_cache 单例
    │     • request_id、channel、settings、endpoint
    │     • http / cache / storage / image 均为惰性属性，用到才建
    │
    └──► script.staged or channel.stages.names ?
          ├─ 是 → execute_staged()  # 级联，见 §3.8
          └─ 否 → execute()         # 单级：auth → request → 上游 → poll → response
         最终 finally 里 ctx.close()：只释放本请求自己创建的资源
```

关键差异（与早期设计稿的对比，便于阅读旧文时对照）：

| 早期设计 | 实际实现 | 原因 |
|---|---|---|
| 解析 body 提取 `model` → Registry 查上游 | 不解析 model，上游由 `X-Upstream-Url` 给定 | 控制面已完成渠道决策，适配器是纯数据面 |
| ctx 在调度器里逐个 new 出 http/redis/minio | lifespan 建进程级单例，ctx 惰性取用 | 每请求新建会丢连接池与 keep-alive |
| `importlib` 按路径加载脚本模块 | `exec()` + `SAFE_BUILTINS`，按 sha256 缓存 | 脚本可能来自 header 文本，无落地路径 |


### 3.3 脚本加载与编译 (`adapter/script_cache.py`)

> 无 `adapter/engine.py`。它的职责被拆成三块：**加载/编译/缓存**在
> `script_cache.py`，**相位调度**在 `executor.py`，**级联驱动**在 `stages.py`。

脚本源码可能来自 header 里的一段文本（无文件路径），因此不能走 `importlib`
按路径加载，而是 `compile()` + `exec()` 进受限命名空间：

```python
# adapter/script_cache.py（要点，非全文）
TRANSFORM_NAME = "transform"

class ScriptCache:                       # 线程安全 LRU，键 = 源码 sha256
    def load(self, source: ScriptSource) -> CompiledScript:
        if hit := self.get(source.sha256):
            return hit                   # 命中即返回，不重复扫描
        scan_source(source.text, ...)    # AST 安全扫描（§3.4）
        code = compile(source.text, filename, "exec")
        namespace = {"__builtins__": SAFE_BUILTINS}   # 无 open/eval/__import__
        exec(code, namespace)                          # 已被扫描 + 白名单双重约束
        fn = namespace.get(TRANSFORM_NAME)             # 必须定义 transform
        # 再读模块级可选声明：PHASES / STAGES / STAGE_FALLBACK
        return CompiledScript(sha256=..., transform=fn, phases=..., stages=...)
```

沙箱的两道闸门都在这一层收口：`SAFE_BUILTINS` 抹掉 `open`/`eval`/`globals`
等一切能触达文件系统与对象图的内置；`__import__` 换成 `_guarded_import`，
在**执行期**再查一次白名单——因为 AST 扫描看不穿 `import urllib.parse`
这类子模块形式，它不能是最后一道防线。

**缓存与失效**：

- 缓存 key 是脚本源码的 `sha256`，不是路径或 `mtime`
- 脚本一改，摘要自然变化，命中新 key 并重新执行 AST 安全扫描
- 因此**不需要** `watchdog` 之类的文件监听，脚本目录只读挂载也不会失效
  （这正是 §3.5.2 里 overlay 卷「改文件免重启」成立的原因）

#### 3.3.1 分层超时模型（v1.1，取代单一 30s 墙钟）

> 以实际代码为准：超时项在 `adapter/settings.py`，阶段调用在 `adapter/executor.py::_call_phase`。

`_call_phase` 对每个 phase 施加 `settings.script_timeout`(30s)，而等待上游的时间落在  
`_do_upstream` 的 `upstream_timeout` 上——两者本就分离，所以 30s 不必放宽。  
级联真正缺的是**跨级的总预算**。六个界各自独立，哪个先到由错误码区分（AC-27）：

| 层级    | 配置项                                                | 代码默认          | 适用                                       | 超时行为                               |
| ----- | -------------------------------------------------- | ------------- | ---------------------------------------- | ---------------------------------- |
| 脚本函数  | `script_timeout`                                   | 30s           | 每个 `transform()` 调用（含 `request:{stage}`） | 504，`code=script_timeout`          |
| 单次图片下载 | `image_download_timeout`                           | 25s           | 相位内 `ctx.download_image` / `image_bytes` / `image_b64` 等 | 504，`code=image_download_timeout`  |
| 单次存储上传 | `storage_upload_timeout`                           | 25s           | 相位内 `ctx.upload_temp_image`                | **降级成 data URI（请求仍成功）**，trace 记 `storage_upload_timeout` |
| 单次上游  | `upstream_timeout`，可被 `ctx.emit(timeout=)` 覆盖      | 60s           | 每级的上游 HTTP 调用                            | 504，`code=upstream_timeout`        |
| 异步作业  | `poll_timeout_default`（`X-Async: timeout=`）        | 300s          | 一个异步 Job 的全部轮询                            | 504，`code=poll_timeout`            |
| 级联总预算 | `stage_budget_default`（上限 `stage_budget_max`）/ `X-Stage-Timeout: total=` | 300s（上限 600s） | 整条级联                                     | 504，`code=pipeline_timeout` + 当前级名 |

⚠️ `script_timeout` 约束的是**脚本函数自身**，而相位内由 `ctx` 发起的 I/O **也算在里面**
——这正是新增 `image_download_timeout` / `storage_upload_timeout` 的理由：在它们存在之前，
一个连不通的客户端图片 URL 会吃满整个相位预算，最后以 `script_timeout` 报出来，把排查引向
脚本与上游两个都不对的层。

**这两个界只负责「报自己」，不负责「掐时间」**——真正兜住失控请求的是 `script_timeout`，
所以它们的取值**紧贴它下方**而不是远低于它：太短会把相位本来来得及完成的活判死
（20MB 图在 1MB/s 下要 20s，15s 的界会把合法的慢下载变成 504），太长（≥ `script_timeout`）
则永远轮不到它先触发，误归因会静默回来。`tests/unit/test_config_keys.py` 钉住了这个大小关系。

**纯 CPU 仍然只受 `script_timeout` 约束**：`asyncio.wait_for` 只在 await 点生效，
而且报出的墙钟包含这段不可中断的 CPU 时间。同理，一个相位里做**多次** I/O 动作时
（如先下载 mask 再上传），各动作的界之和仍会超过相位上限，此时先触发的依旧是
`script_timeout` —— 那是诚实的答案，不是缺陷。

> 表里是**代码默认值**（`adapter/settings.py`）。`.env` 实际把 `upstream_timeout` 提到 **600s**、  
> 把 `poll_timeout_default` 提到 **300s**，两者不一致时以 `.env` 为准。
> 注意**不存在** `pipeline_max_timeout` 配置项，也**没有**独立的「单级超时」项——单级上游调用用的就是 `upstream_timeout`
> （代码见 `adapter/stages.py::execute_staged` 与 `adapter/executor.py::_do_upstream`）。

关键规则（BR-011）：单次上游的实际超时取 `min(plan.timeout or upstream_timeout, budget.remaining)`，  
故各级超时**不会相加溢出总预算**。未声明 `STAGES` 的脚本行为完全不变。

### 3.4 安全沙箱 (`adapter/sandbox.py`)

```python
# adapter/sandbox.py（要点，非全文）
class SandboxScanner(ast.NodeVisitor):
    """命中第一条违规即抛 SecurityError。"""

    def visit_Import(self, node):        # import x —— 必须全限定命中白名单
        for alias in node.names:
            if alias.name not in ALLOWED_STDLIB:
                raise SecurityError(f"Forbidden import: {alias.name}")
        self.generic_visit(node)

    def visit_ImportFrom(self, node):    # from x import y；顺带禁相对导入
        if node.level != 0:
            raise SecurityError("Relative imports are not allowed in scripts")
        if (node.module or "") not in ALLOWED_STDLIB:
            raise SecurityError(f"Forbidden import from: {node.module}")
        self.generic_visit(node)

    def visit_Attribute(self, node):     # 关键：封堵沙箱逃逸家族
        if node.attr.startswith("__") and node.attr.endswith("__"):
            raise SecurityError(f"Forbidden dunder attribute access: {node.attr}")
        self.generic_visit(node)

    def visit_Name(self, node):          # 不只拦调用，连别名都拦（f = eval）
        if node.id in FORBIDDEN_NAMES:
            raise SecurityError(f"Forbidden name reference: {node.id}")
        self.generic_visit(node)

    def visit_Global(self, node):        # 跨相位状态请用模块级 dict
        raise SecurityError("global statements are not allowed in scripts")
```

三条策略，各自封堵一类逃逸：

| 策略 | 拦什么 | 为什么必需 |
|---|---|---|
| import 白名单 | `aiohttp`/`redis`/`minio`/适配器内部模块 | 基础设施只能经 `ctx` 触达，脚本拿不到裸连接 |
| `FORBIDDEN_NAMES` | `exec`/`eval`/`compile`/`open`/`globals`/`getattr`… | 拦的是 **Name 节点**而非 Call，故 `f = eval` 这类别名绕法同样命中 |
| dunder 属性 | `().__class__.__bases__[0].__subclasses__()` | 这是 Python 沙箱最经典的逃逸链，只禁 `exec`/`eval` 挡不住 |

**`Subscript` 与 `Await` 是刻意放行的**：脚本是 async 函数、且全程操作 dict，
禁掉它们等于禁掉脚本本身。（早期设计稿把这两个列进黑名单，与实现不符。）

**允许的标准库清单**（以 `sandbox.py::ALLOWED_STDLIB` 为准，23 项）：
`json`, `re`, `base64`, `binascii`, `datetime`, `time`, `math`, `random`,
`string`, `typing`, `collections`, `collections.abc`, `itertools`, `functools`,
`hashlib`, `hmac`, `uuid`, `urllib.parse`, `textwrap`, `decimal`, `enum`,
`dataclasses`, `copy`

注意白名单要求**全限定匹配**：`urllib.parse` 在列而裸 `urllib` 不在，
`import urllib` 会被拒。子模块形式（`import urllib.parse`）AST 层看不穿，
由 §3.3 的 `_guarded_import` 在执行期兜住。


### 3.5 上下文对象 (`adapter/context.py` + `adapter/ctxapi/`)

脚本与基础设施交互的唯一通道。**装配根与能力实现分离**：`context.py` 只留
per-request 状态、惰性基础设施句柄与生命周期（`ContextCore`），所有脚本可见
的工具方法按关注点拆进 `adapter/ctxapi/` 的 mixin，由 `AdapterContext` 组装：

```python
class AdapterContext(
    CodecMixin,      # ctxapi/codec.py     base64 / data URI / MIME 嗅探
    ImageRefMixin,   # ctxapi/image_ref.py 下载 + 三形态互转
    StorageMixin,    # ctxapi/storage.py   bytes -> URL（经 adapter/storage 端口）
    BudgetMixin,     # ctxapi/budget.py    remaining / deadline
    PlanMixin,       # ctxapi/plan.py      RequestPlan + emit()
    ContextCore,     # context.py          状态 / http / cache / storage / close
):
    SKIP = SKIP
```

为什么这样拆：工具方法的变更频率远高于生命周期，过去两者同处一个类，
每加一个 helper 都要改动持有请求状态的文件。拆开后**新增能力 = 新增一个
模块文件 + 基类列表加一个名字**，`ContextCore` 不动。

组装规约（破坏其一就会引入隐蔽故障，改动时必须守住）：

| 规约 | 原因 |
|---|---|
| mixin 一律不定义 `__init__` | 否则基类顺序变成语义相关，MRO 一改就出错；状态全由 `ContextCore` 建 |
| mixin 只经 `ContextCore` 暴露的属性碰基础设施 | 保证脚本侧无法绕过 `settings`/`http`/`cache`/`storage` 拿到裸连接 |
| 跨 mixin 调用走 `self`，并继承 `Needs*` 标记声明依赖 | 纯 `self.x()` 调用类型检查器看不见，签名漂移会静默失效 |
| `ContextCore` 排在基类**最后** | mixin 永远无法意外遮蔽基础设施句柄 |
| 方法名在各 mixin 间不得重名 | 有 `test_ctx_composition.py` 机械校验 |

脚本侧**语法完全不变**（`ctx.image_b64(...)` 仍是平铺方法），mixin 是纯内部
结构。`CTX_MIXINS` 是登记表，单测断言它与真实 MRO 一致，防止文档与代码漂移。

引擎侧不再戳私有属性：级联预算用 `ctx.attach_budget(budget)`，相位间清计划用
`ctx.reset_plan()`。

现有能力清单：`http`/`cache`/`storage`/`image`/`emit`/`download_image`/
`upload_temp_image`/`image_bytes`/`image_b64`/`image_data_uri`/`image_url`/
`encode_b64`/`decode_b64`/`data_uri`/`sniff_mime`/`is_url`/`is_data_uri`/
`sleep`/`remaining`/`deadline`/`stage`/`stage_urls`/`SKIP`。

分清单里两类的区别：`image_bytes`/`image_b64`/`image_data_uri`/`image_url` 是
**三态分派**入口（远程 URL / data URI / 裸 base64，内部按 `is_url` 分叉）；
`download_image` **不是**它们之一，而是 `image_bytes` 的 URL-only 半支。客户端图片
走了它（vision 脚本最常犯的错）会以 `invalid_request`（400，`param="image"`）拒绝，
消息里点名该用的方法——**此前**由 `check_url` 以 `channel_config_error` 报出，
把脚本 bug 归因成控制平面配错了头。改成 `invalid_request` 是归因修正：控制平面若按
error code 分流（如把 `channel_config_error` 当渠道故障告警），需同步这一条。

`ctx.emit()` 决定上游请求体的**载体**，三选一：返回值走 JSON；
`form=` 走 `application/x-www-form-urlencoded`；`files=` 走
`multipart/form-data`——返回值作文本字段（与 `form` 合并），`files` 作二进制部件，
boundary 与 Content-Type 由引擎生成，脚本只交字节。`files` 的字段值是一个部件
`("a.png", bytes, "image/png")` 或部件列表（同名字段重复时用列表）。它存在的
唯一理由是 OpenAI 原生 `/v1/images/edits` 只接受文件上传，JSON body 无法表达；
实现落在 `adapter/ctxapi/plan.py`（归一化）与 `adapter/transport.py`
（`build_multipart`），脚本 `openai/images@v1` 是它的第一个使用者。

#### 3.5.1 级联编排增强能力（v1.1）

> 以实际代码为准：能力清单见 §3.5，实现分布在 `adapter/ctxapi/` 各 mixin。
> 下表是 v1.1 级联相对基础能力新增的部分。

| 新增                               | 用途                                                          | 备注                            |

#### 3.5.2 脚本存储：可插拔后端与双部署形态

`X-Script-Ref` 的解析拆成**策略**与**查找**两层，避免新增存储后端时误绕安全闸门：

| 层 | 位置 | 职责 |
|---|---|---|
| 策略 | `adapter/script_source.py` | 尺寸上限、`X-Script-Sha256` 钉死、digest 白名单、SSRF 与远端 host 校验 |
| 查找 | `adapter/scriptstore/` | ref 语法解析 + 按后端取源码文本，**不含任何策略** |

后端契约只有一个方法，新增 Git / S3 / HTTP 目录后端只需实现它并在
`build_store()` 里插入位置，调用方零改动：

```python
class ScriptStore(Protocol):
    name: str
    async def get(self, ref: ParsedRef) -> str | None: ...   # None = 本后端没有
```

**可选清单 `manifest.json`**（每个根一份，`scriptstore/manifest.py`）：让
「移动标签」和「摘要审计」成为可能——这两件事裸目录表达不了。

```json
{
  "scripts": {
    "volcengine_ark/images": {
      "latest": "v1",
      "aliases": {"stable": "v1"},
      "digests": {"v1": "7bb5c4cb..."}
    }
  }
}
```

| 能力 | 效果 | 约束 |
|---|---|---|
| `aliases` | `X-Script-Ref: volcengine_ark/images@stable` 解析到 `@v1` | 改一处清单即可整体前移，无需改每个渠道头 |
| `latest` | 隐式别名，`@latest` 直接可用，不必在 `aliases` 里重复 | 显式 `aliases` 条目优先于 `latest` 字段 |
| `digests` | 声明各版本 sha256 | **默认只声明不强制**，由 `SCRIPT_PIN_MANIFEST_DIGESTS` 打开强校验 |

三个刻意的设计取舍：

1. **清单严格可选**。没有 `manifest.json` 时，ref 必须写具体版本——与加清单
   之前的行为完全一致。清单是文件名约定的**追加**，不是使用它的前提。
2. **清单损坏不报错，只降级**。非法 JSON / 结构不对 / `aliases` 写成数组，
   一律当作「无清单」并记 warning。可选 overlay 文件里的一个手误，不该让
   其它所有 ref 一起解析失败。
3. **摘要默认不强制**。清单表达的是意图，而一个未签名的本地文件不该变成
   卡死正常部署的硬闸门；要强校验就显式打开 `SCRIPT_PIN_MANIFEST_DIGESTS`。
   别名环（`a→b→a`）有深度上限，只会 miss，不会挂住请求。

`ChainStore` 按顺序取第一个命中，并严格区分两种情形——**「本后端没有」
（`None`，继续找下一个）与「本后端坏了」（抛错，立即失败）**。这个区分是必需的：
文件缺失应回落到下一个根，而文件存在但读不出来若也静默回落，就会悄悄用上
一个更旧版本的脚本。别名解析在**触碰文件系统之前**完成，所以某个根独有的
别名不会把请求引到别的根去。

**两种部署形态同时兼容，默认读镜像内置：**

| 顺序 | 后端 | 来源 | 说明 |
|---|---|---|---|
| 1 | overlay | `SCRIPT_OVERLAY_DIRS`（逗号分隔，默认空） | 只读卷挂载；免重建镜像热修脚本 |
| 2 | image | `SCRIPT_REF_DIR`（默认 `/app/script_store`） | 随镜像打包，恒存在，无宿主路径依赖 |

不配 overlay 时链上只有 image 后端，即**默认行为 = 读镜像里的 `script_store`**，
容器可被调度到任意节点。目录不存在只是跳过而非报错，所以「先上镜像、以后再决定
要不要挂卷」不需要改代码。又因 `ScriptCache` 以源码 sha256 为键，挂载目录里改
文件即换键，**改脚本无需重启**。

每个根支持两种布局：`<root>/vendor_y/mj@v1.3.py`（扁平）与
`<root>/vendor_y/mj/v1.3.py`（嵌套）。ref 段名走严格白名单正则，`.`/`..`
与分隔符无法通过，因此路径穿越在触碰文件系统之前就被拒；此外每个候选路径
仍做一次 `is_relative_to(root)` 复核，用于挡住根目录内指向外部的符号链接。


### 3.6 上游注册表（已作废，未实现）

> **本节为早期设计稿，不对应任何代码。** `adapter/registry.py` 与
> `config/upstreams.yaml` 都不存在，也不会存在。保留此节仅为记录架构演进。

原设计打算用 YAML 注册表集中登记上游（`base_url` / `auth_type` /
`env_key` / `models` / `endpoints`），凭据由适配器从进程环境读取。

**实际架构改为通道自描述**，原因有二：

1. **适配器不持有上游密钥。** 凭据由控制面随请求经 channel header 传入
   （`Authorization` / `X-Auth-Emit`），脚本无法访问进程环境
   （见 `adapter/context.py` 模块注释）。因此 `env_key` / `ak_env` /
   `sk_env` 这类字段没有落点。
2. **上游形态差异太细，配不动。** 同一厂商不同模型变体的字段矩阵都不一样
   （如 `image` 字段的 URL / data URI / 裸 base64 支持情况互不相同），
   这类差异只能由脚本表达，注册表反而成了二次抽象。

现行做法：上游地址与超时由请求头声明（`X-Upstream-Url` 等），
模型映射与字段改写由脚本 `transform(ctx, payload, phase)` 负责，
级联由脚本模块级 `STAGES` 加 `X-Stages` / `X-Stage-Urls` /
`X-Stage-Timeout` 覆盖，详见 §3.8.2 与 §3.8.6。


### 3.7 异步 Job 轮询 (`adapter/executor.py::_run_poll_loop`)

> 无 `adapter/async_state.py`，也没有 `AsyncStateMachine` 类。上游 Job 轮询是
> `executor.py` 里的一个函数；`adapter/state_store.py` 是**另一件事**——它服务
> `/v1/responses` 的多轮状态链（`resp_ctx:{id}`），与上游轮询无关，别混淆。

上游是 Job 模式时（控制面置 `X-Async`），引擎驱动脚本的两个轮询相位：

```python
# adapter/executor.py::_run_poll_loop（要点，非全文）
async def _run_poll_loop(script, ctx, channel, settings, first, *, budget, stage):
    spec = channel.async_spec
    deadline = time.monotonic() + spec.timeout
    handle = first.payload                     # 首次响应即 Job 句柄
    attempts = 0

    while True:
        if time.monotonic() >= deadline:
            raise PollTimeoutError(spec.timeout)
        if budget is not None and budget.exhausted:      # 级联总预算优先于单级
            raise PipelineTimeoutError(budget.total, stage)
        attempts += 1
        if attempts > settings.poll_max_attempts:        # 双闸：时间 + 次数
            raise PollTimeoutError(spec.timeout)

        interval = spec.poll_interval
        if budget is not None:
            interval = budget.cap(interval)    # 绝不睡过预算，否则 504 会迟到
        await asyncio.sleep(interval)

        ctx.reset_plan()                                   # 清上一轮的 emit
        poll_body = await _call_phase(script, ctx, handle, PHASE_POLL_REQUEST, ...)
        reply = await _do_upstream(ctx, channel, settings, poll_body, ...)
        verdict = await _call_phase(script, ctx, reply.payload, PHASE_POLL_RESPONSE, ...)

        if not isinstance(verdict, dict):      # 契约：必须返回带 done 键的 dict
            raise ScriptRuntimeError(PHASE_POLL_RESPONSE, "must return a dict ...")
        if verdict.get("error"):
            raise UpstreamError(f"Upstream job failed: ...")
        if verdict.get("done"):
            return verdict.get("payload", reply.payload)
        handle = verdict.get("payload", handle)            # 句柄可被脚本更新
```

与早期设计稿的三处实质差异：

| 早期设计 | 实际实现 | 原因 |
|---|---|---|
| 脚本实现 `handle_async_job()` 具名钩子 | 复用单入口 `transform(ctx, payload, "poll_request"/"poll_response")` | 全局只有一个脚本入口约定（§8.1） |
| Redis 分布式锁防多 Worker 重复轮询 | **无锁** | 轮询由持有该 HTTP 连接的 worker 独占驱动，本就不存在第二个轮询者；引 Redis 会让 Job 模式硬依赖 Redis |
| 仅时间超时 | 时间 + `poll_max_attempts` + 级联总预算三重 | 上游返回极小 `poll_interval` 时，单靠时间闸会打出海量请求 |

脚本若未声明 `PHASES` 覆盖两个 poll 相位，而控制面又置了 `X-Async`，
引擎直接报 `ChannelConfigError`——配置矛盾即刻暴露，不进轮询循环。


### 3.8 级联编排 (`adapter/stages.py`，v1.1)

> 本节以**实际代码结构**为准（channel 头驱动 + `transform(ctx, payload, phase)` 单入口），  
> 而非 §3.2/§3.6 遗留的 registry/YAML 描述。
>
>

#### 3.8.1 为什么现有引擎不够

`executor.execute()` 的链路是固定的：`auth → request → 【1 次上游调用】→ [poll] → response`。  
上游调用由引擎独占，脚本只能描述**一次**请求。级联需要 N 次调用，且第 2 次的入参依赖第 1 次的产物，  
现有阶段机无法表达。

#### 3.8.2 方案：新增 `stages` 阶段，引擎驱动多轮

不改变「脚本不碰 socket、引擎不懂厂商语义」这一根本约定，只把「一轮」扩展为「按脚本声明的 N 轮」。

脚本通过模块级 `STAGES` 声明级联，引擎逐级驱动：

```python
# script_store/vendor_x/hd@v1.py
PHASES = ["request", "response"]
STAGES = ["generate", "upscale"]        # 声明级联，引擎按序执行

async def transform(ctx, payload, phase):
    # 前处理：纯本地计算，不产生上游调用
    if phase == "request:generate":
        ctx.emit(url=ctx.options["generate_url"])
        return {"prompt": payload["prompt"], "size": "2k"}

    if phase == "response:generate":
        # 产物存入 ctx.stage，供下一级引用
        return {"image": payload["data"][0]["url"]}

    if phase == "request:upscale":
        ctx.emit(url=ctx.options["upscale_url"], timeout=120)
        return {"image": ctx.stage["generate"]["image"], "scale": 2}

    if phase == "response:upscale":
        return {"created": 0, "data": [{"url": payload["output"]}]}
```

阶段命名规则：`{phase}:{stage}`。未声明 `STAGES` 的脚本，phase 名不带后缀，  
走原有单轮链路——**既有脚本与既有测试零改动**（AC-25）。

#### 3.8.3 引擎侧实现

```python
async def execute_staged(ctx, script, channel, settings, client_payload):
    """按 STAGES 逐级驱动；每级复用既有的单轮逻辑。"""
    budget = Budget(total=resolve_total(
        channel.stages.budget, settings.stage_budget_default, settings.stage_budget_max
    ))
    ctx.stage = {}                       # 级间产物，脚本只读引用

    payload = client_payload
    for name in script.stages:
        with logfire.span("stage", name=name, remaining_s=budget.remaining) as span:
            ctx.plan = RequestPlan()
            body = await _call_phase(script, ctx, payload, f"request:{name}",
                                     settings.script_timeout)
            if body is SKIP:                  # AC-31：整级跳过，不发上游调用
                span.set_attribute("skipped", True)
                continue
            try:
                reply = await _do_upstream(ctx, channel, settings, body,
                                           budget=budget)
                if channel.async_spec.enabled:
                    reply = await _run_poll_loop(script, ctx, channel, settings, reply)
                out = await _call_phase(script, ctx, reply.payload,
                                        f"response:{name}", settings.script_timeout)
            except AdapterError as exc:
                if not _fallback_ok(script, name, ctx.stage):
                    raise
                span.set_attribute("degraded", True)
                logfire.warn("stage_degraded", stage=name, reason=str(exc))
                break                     # 降级：返回上一级产物
            ctx.stage[name] = out
            payload = out
    return _final_payload(ctx.stage)
```

关键点：

- **复用而非重写**：`_do_upstream` / `_run_poll_loop` / `_call_phase` 全部沿用，级联只是外层循环。
- **每级独立的 `ctx.plan`**：`emit()` 的 URL/method/timeout 覆盖按级隔离，不串味。
- **异步 Job 正交**：任一级都可以是 job 型上游，`poll_*` 阶段在该级内部完成。

#### 3.8.4 共享预算（取代单级超时相加）

```python
@dataclass
class Budget:
    total: float
    started: float = field(default_factory=time.monotonic)

    @property
    def remaining(self) -> float:
        return max(0.0, self.total - (time.monotonic() - self.started))
```

`_do_upstream` 的实际超时取 `min(plan.timeout or upstream_timeout, budget.remaining)`；  
`remaining <= 0` 直接抛 `PipelineTimeoutError`。这样各级超时**不会相加溢出总预算**（BR-011）。

#### 3.8.5 降级

`STAGE_FALLBACK = ["upscale"]` 声明哪些级可降级。该级失败且 `ctx.stage` 已有可用产物时，  
中断级联、返回上一级结果，响应头置 `X-Adapter-Degraded: upscale` 与  
`X-Adapter-Degraded-Reason: <error code>`，HTTP 仍为 200（BR-013）。  
后处理（超分/转码）适用；**首级不可降级**（无上一级产物可退，`STAGE_FALLBACK` 含首级时  
脚本加载期即报错）。

降级产物需要重新塑形：中间产物是级间交接形状，不是客户端响应。脚本在 `PHASES` 里声明  
`degraded` 后，引擎会以该 phase 回调一次，把手上的产物转成客户端 body（见 §3.8.10）。

#### 3.8.6 通道声明

级联同样由控制面通过 header 声明，与现有 channel 模型一致：

```
X-Stages:         generate,upscale                     # 覆盖脚本 STAGES（可选）
X-Stage-Urls:     generate=https://a.com/t2i,upscale=https://b.com/sr
X-Stage-Timeout:  total=300
```

`X-Stage-Urls` 的每个 URL 同样过 `check_url()` 的 SSRF 校验；脚本经 `ctx.options` /  
`ctx.stage_urls` 读取，凭证仍由引擎按 `X-Auth-Emit` 注入，不进脚本可见域（BR-014）。

#### 3.8.7 `ctx.image`：前处理算子

Pillow 已在 requirements（`pillow==12.3.0`）但未对脚本暴露。实现为受限门面  
（`adapter/utils/imageops.py`，bytes 进 bytes 出，无文件路径参数）：

```python
class ImageOps:
    """CPU 密集操作一律走 asyncio.to_thread，不在事件循环里直接调 PIL。"""
    async def info(self, data) -> dict: ...                 # 宽高/格式/模式
    async def resize(self, data, width, height,
                     keep_ratio=True, fmt=None) -> bytes: ...
    async def convert(self, data, fmt, quality=None) -> bytes: ...
    async def to_data_url(self, data) -> str: ...
```

沙箱白名单**不放宽**——脚本仍不能 `import PIL`，只能 `await ctx.image.resize(...)`。

防护（BR-012）：

- 解码前设 `Image.MAX_IMAGE_PIXELS` 并按 header 声明的宽高校验 50 MP 上限  
  （`settings.max_image_pixels`），**在 `load()` 分配位图之前**拦截解压炸弹；  
  Pillow 自身在 2× 上限处抛 `DecompressionBombError`，已归一为同一个  
  `code=image_too_large`。
- 输出复用 `settings.max_asset_bytes`（20 MB）上限。
- 输入/输出格式限定 PNG / JPEG / WEBP / GIF；JPEG 无 alpha 通道，RGBA 源自动展平。

> 设计稿列出的 `crop` / `pad` / `compress` / `compose_mask` 本次未实现——`compress`  
> 的语义已由 `convert(fmt, quality=)` 覆盖，其余三个在当前级联场景（缩放 + 转码）  
> 无调用方，按 YAGNI 暂缓，待有真实脚本需求再加。

#### 3.8.8 整级跳过（`ctx.SKIP`）

同一脚本要同时服务文生图与图生图时，`preprocess` 级在无入图的请求里无事可做。  
`request:{stage}` 返回哨兵 `ctx.SKIP` 即整级跳过——不发上游调用、不写 `ctx.stage`、  
不消耗预算，直接进入下一级（AC-31）：

```python
if phase == "request:preprocess":
    if not payload.get("image"):
        return ctx.SKIP                  # 文生图：无入图，跳过前处理
    return {"image": await ctx.image.resize(..., 1024, 1024)}
```

引擎侧在 `_call_phase` 返回后判定 `body is ctx.SKIP` 则 `continue`，  
Span 标 `skipped=True`。哨兵是模块级单例，不可被脚本构造，避免与合法 payload 混淆。

#### 3.8.9 批量放大控制

`n > 1` 时上游调用量为 `n × len(STAGES)`。约束（BR-015）：并发上限 `settings.stage_concurrency`（默认 3）；  
限流按实际上游调用次数而非请求数计费；`adapter_stage_upstream_calls_total` 独立暴露以便容量核算。

#### 3.8.10 实现落地时的设计调整（vs 设计稿）

实现过程中与 §3.8.2~3.8.8 设计稿有几处有意偏离，均为了简化或补足语义：

1. **阶段名走 `request:{stage}` / `response:{stage}`，`degraded` 单独成 phase**。  
   级联中某级失败降级时，`ctx.stage` 里拿到的中间产物是**级间交接形状**（如  
   `{"image": ...}`），不是合法的客户端响应（应为 `{"created":..,"data":[...]}`）。  
   因此降级分支若直接用上一级产物会返回一个残缺 body。新增 `degraded` phase（须在  
   `PHASES` 里显式声明），由脚本把中间产物重新塑形为客户端响应。
2. **预算检查点放在 `_do_upstream` 入口**，超时也归并到该函数统一分类。未声明 `STAGES` 时  
   `budget=None`、`stage=None`，行为与现状完全一致。
3. **`ctx.SKIP` 的判定用 `body is ctx.SKIP`**，哨兵是模块级单例 `_Skip`，不可被脚本构造，  
   `bool(ctx.SKIP)` 恒为 `False`——防止脚本把 skip 误当空 body 处理。
4. **`X-Stage-Urls` 的每个 URL 同样走 `check_url()`**，且要求 URL 键是 `X-Stages` 键的子集  
   （拼写错误的级名会在解析期被拒绝，而非静默路由到通道 URL）。
5. **stage 数量双上限**：脚本侧 `STAGES` 声明上限 8（`MAX_DECLARED_STAGES`），  
   控制面 `X-Stages` 覆盖上限 `settings.stage_max_count`（默认 8）。
6. **`context.py` 已超 300 行**（476），是历史遗留，本次未重构；其余涉及文件均在规范内。

没有独立的 `AsyncStateMachine` 协作者。

```
Client        api/pipeline      executor._run_poll_loop    Script        Upstream
  │               │                        │                 │             │

  │               │                        │                 │             │

  │               │                        │                 │             │
```

#### 各 Span 的属性契约

`script_phase`（`adapter/executor.py::_call_phase`；由 `tests/integration/test_script_phase_span.py` 钉住）：

| 属性 | 何时写入 | 含义 |
| --- | --- | --- |
| `phase` | 构造时 | `auth` / `request` / `response` / `poll_request` / `poll_response`，级联时带 `:<stage>` 后缀 |
| `timeout` | 构造时 | 该相位的墙钟上限（即 `SCRIPT_TIMEOUT`） |
| `elapsed_ms` | 结束时（含失败与超时） | 该相位实际耗时 |
| `outcome` | 结束时 | `ok` / `timeout`（被上限掐断）/ `error`（脚本报错） |
| `error_code` | 仅 `outcome != ok` | 超时固定为 `script_timeout`；脚本 `ctx.fail` 时是它给的 code |

`outcome` 是这张表里最要紧的一列：**没有它，「跑了 28 s 自己结束」与「30 s 被掐断」是同一个 span**，
而两者要查的方向完全不同。

`download_image`（`adapter/ctxapi/image_ref.py::download_image`）：`url`（截断到 `URL_LIMIT`）、
`cache_hit`、`size_bytes`、`elapsed_ms`、`outcome`、`error_code`（失败时）。
它是唯一能把「客户端的图慢」与「厂商慢」分开的 span —— 两者在上层都只是"相位跑了很久"。
`storage_put`（`adapter/ctxapi/storage.py::upload_temp_image`）：`store`、`bytes`、`ext`、
`elapsed_ms`、`outcome`、`error_code`（失败时）。**降级成 data URI 的那条路径只有这里看得见**：
请求仍然是 200，客户端拿到的是 base64 而不是链接，trace 是唯一的记录。

`upload_temp_image` 与 `download_image` 都遵循同一隐私口径：**完整对象 key 不上报**
（key 里含 request-id 与 uuid），**base64 内容永不离开进程**（见下方"客户端上下文"）。

`phase_ms` / `phase_calls`（`adapter/trace_attrs.py::phase_summary`）：按相位名累计的毫秒数与
调用次数，让根 span 能直接回答「这个请求里脚本一共占了多少」。两者都是 dict，Logfire 会把它们
导出为 **JSON 文本**并附一条 `logfire.json_schema` 说明其形状；在原始 span 上读到的因此是字符串，
断言前要 `json.loads`（纯 OTel exporter 无此包装，两种 exporter 的断言写法不可互相照搬）。

`upstream_call` 的属性契约由 `tests/integration/test_upstream_span.py` 钉住：成功调用、上游 5xx、
响应体超限被拒**三种情况都必须带 `status`**（状态行先于 body 读取即确定，含被拒路径），
而连接失败**必须不带**（不伪造状态码，缺失即代表"从未收到应答"）。
同一规则适用于后加的 `response_bytes`：**只在响应体真的读完时写入**，
所以"没读到字节"与"读到 0 字节"在 trace 里仍然分得开。

#### 客户端上下文（`adapter/trace_attrs.py`）

`adapt` / `cascade` 还带**客户端请求上下文**，属性在 **Span 构造时**写入（不是上游返回之后）：
`prompt`（截断 2000 字符）、`prompt_chars`（原始长度，使截断可见）、`model`、
`image_urls` / `mask_urls`（仅 http(s) 引用，每项截断 2000）、
`image_inline_refs` / `mask_inline_refs`（data URI 与裸 base64 的**计数**）、
`image_urls_truncated`（仅在超过 8 条上限时出现）。

**回答侧**（`result_urls` / `result_urls_truncated` / `result_inline_refs`）在脚本产出结果后
写入：只读规范契约的 `data[]`，`url` 是 http(s) 就上报链接，`b64_json` 或顶着 `url` 键的
data URI 只计数——既回答「成功了但图在哪」，也把「没图」与「图是 base64（`response_format=
b64_json`，或未配对象存储时 `url` 的降级形态）」区分开。脚本改以 chat / responses 原生形态
作答时（包装层会让路）不猜结构、只留空：遍历未知结构会把调用方的输入回显和厂商无关链接
当成产出图上报。

其中两个属性同时充当 **GenAI 语义约定的身份字段**，使 span 被当成模型调用而不是普通 HTTP 请求
（Logfire 认的是属性名，不是 instrumentation 来源 —— 它自己的集成也只是 `span.set_attribute`）：
`gen_ai.operation.name=image_generation`、`gen_ai.request.model`（= 客户端**请求**的模型，与既有 `model` 同值）。

⚠️ 两处刻意的选择：**`image_generation` 是 Logfire 的拼法，不是规范枚举**（GenAI 约定里没有图像专用
operation，多模态写作 `generate_content` + `gen_ai.output.type=image`；本服务以 Logfire 为读者，故用它的词表）；
**`gen_ai.provider.name`（及废弃别名 `gen_ai.system`）刻意不写** —— 词表里没有 `volcengine_ark`，
中转卖家更是无 enum 可对，猜一个值会让 trace 里出现看似事实的假信息。`gen_ai.response.model` 同理留空
（真正作答的模型是渠道的事）。这延续本仓库的取向：**「没有事实」是一等公民**。
判据由 `tests/unit/test_trace_attrs.py` 钉住（含「不伪造 provider」的反向断言）。

⚠️ **一个必须知道的连带效果**：Logfire 的导出层 `_default_gen_ai_response_model`
（`processor_wrapper.py`，在**每个 span 结束时无条件执行**）会在 span 缺 `gen_ai.response.model` 时
把它**填成请求模型**。所以真实 trace 会多出一条 `gen_ai.response.model`，读起来像「请求的模型作答了」。
这是**平台默认行为**，不是本适配器的断言。运维含义：对 `volcengine_ark`（脚本丢弃 body 里的 model、
改用渠道 options 的接入点 ID）那一列显示的是**客户端的路由标签**，不是接入点 ID —— 排查时看
`upstream_url` 与脚本，别把该列当成厂商侧的实际模型。

两条规则。**base64 一律不出进程**：引用图本身就是图，20MB 引用会在每次失败时变成
27MB 的属性导出；只计数，从而仍能区分「没传图」（属性缺失）与「传了 inline 图」
（`image_inline_refs` 有值）——multipart 上传全部落在后者。**该函数绝不抛异常**：
它在 Span 打开之前运行，一次异常会把本该成功的请求变成 500，即"改可观测性反而打断流量"。

价值全在失败路径：上游 400（内容合规拒绝是典型案例，其报文既不含 prompt 也不含引用图）
必须仍带 `prompt` 与 `image_urls`，由 `tests/integration/test_request_context_span.py`
以**假上游返回 400**的方式钉死——只断言成功路径会漏掉"属性写在上游调用之后"这一失效形态。
属性名与两个 Span 自身的构造参数是邻居，重名即 TypeError，故 `tests/unit/test_trace_attrs.py`
用满载属性真实构造两种 Span 钉住。

数组属性（`image_urls`）落到 span 上会被 Logfire 序列化为 JSON 文本，并附一条
`logfire.json_schema` 声明其为 array（UI 据此渲染成数组）；读原始 span 需 `json.loads`。

#### 前置门失败的补记（`ingress_failed`）

`execute` **之前**的失败曾经只留下一个 HTTP 状态：准入、body 解析、校验、channel 解析、
脚本加载这五步都跑在任何 span 打开之前，而最需要 prompt 的场景恰恰在其中
（`validate_images_body` 的 400、`channel_config_error` 的 400、准入 401）。

`adapter/api/pipeline.py` 把这五步包进 `except AdapterError`，命中时由
`trace_attrs.record_ingress_failure` 开一个 **`ingress_failed`** span 再重抛：

| 属性 | 何时写入 | 含义 |
| --- | --- | --- |
| `endpoint` | 构造时 | 与根 span 同值 |
| `stage` | 构造时 | 死在哪一步：`admission` / `body` / `validation` / `channel` / `script` |
| `status` | 构造时 | 出口状态码 |
| `error_code` | 构造时 | `AdapterError.code` |
| 客户端上下文 | 构造时 | 与根 span 同一套（`prompt` / `image_urls` / …），**唯独不带 `gen_ai.*`** |

三条刻意的性质：

- **属性集随 stage 稀疏，不是齐的。** `admission` 与 `body` 阶段 body 还没解析出来，
  span 上只有 `endpoint` / `stage` / `status` / `error_code`——**没有 `prompt`**。
  「当时读得到什么就记什么」是这张表一半的价值：一个看起来齐整的属性集，
  会让「还没读」与「确实没有」再也分不开。
- **不带 `gen_ai.*`**（`summarise_request(..., genai=False)`）。前置门拒绝没有发生任何模型调用；
  写上 `gen_ai.request.model` 不只是多一个字段——Logfire 的导出层会据此镜像出
  `gen_ai.response.model`，把一次从未发出的调用写成「模型答复了」。
- **只捕 `AdapterError`。** `CancelledError` 是 `BaseException`，必须继续向上传播；
  包住它会让相位上限（`script_timeout`）静默失效。

判据在 `tests/integration/test_ingress_span.py`（六个用例，含两条反向断言：成功请求**不得**
产生该 span、该 span **不得**出现 `gen_ai.*`；已用变异验证——注释掉补记调用即 5 项变红）。

**仍不在覆盖范围内**：middleware 层（body 上限 413、限流 429、CORS）与路由级 404/405、
FastAPI 422——它们在 `adapt` 被调用之前就结束了。上报的是**客户端折叠后**的 prompt，
不是脚本改写后真正发给上游的那份（`apply_auth` 会把凭据写进 body，故整体上报上游 body
需要先摘字段，本特性刻意不碰）。

## 8. 接口契约

### 8.1 脚本标准接口

> 以实际代码为准（`adapter/script_cache.py::TRANSFORM_NAME`）：脚本只有**一个入口函数**，  
> 用 `phase` 参数区分职责，而非多个具名钩子。

```python
# 唯一必需入口。phase ∈ {auth, request, response, poll_request, poll_response}
# 级联时 phase 形如 "request:generate" / "response:upscale"（§3.8.2）
async def transform(ctx, payload, phase): ...

# 可选模块级声明
PHASES = ["request", "response"]          # 需处理默认之外的阶段时显式声明
STAGES = ["generate", "upscale"]          # v1.1：声明级联，引擎按序驱动
STAGE_FALLBACK = ["upscale"]              # v1.1：允许降级的级
```

`PHASES` 的既有校验规则不变：必须包含 `request`/`response`，未知阶段名报 `SecurityError`。  
`STAGES` 缺省时 phase 名不带后缀，行为与现状完全一致（AC-25）。

### 8.3 级联脚本示例（生图 + 超分）

```python
# script_store/vendor_a/images_hd@v1.py
STAGES = ["generate", "upscale"]
STAGE_FALLBACK = ["upscale"]              # 超分失败则返回原图

async def transform(ctx, payload, phase):
    # 前处理：入图归一化，纯本地计算，不产生上游调用
    if phase == "request:generate":
        src = payload.get("image")
        if src:
            raw = await ctx.image_bytes(src)
            meta = await ctx.image.info(raw)
            if meta["width"] > 1024 or meta["height"] > 1024:
                raw = await ctx.image.resize(raw, 1024, 1024, keep_ratio=True)
            payload = {**payload, "image": ctx.encode_b64(raw)}
        ctx.emit(url=ctx.stage_urls["generate"])
        return {"prompt": payload["prompt"], "width": 1024, "height": 1024}

    if phase == "response:generate":
        return {"image": payload["image_url"]}

    # 后处理：超分。读上一级产物
    if phase == "request:upscale":
        ctx.emit(url=ctx.stage_urls["upscale"], timeout=120)
        return {"image": ctx.stage["generate"]["image"], "scale": 2}

    if phase == "response:upscale":
        return {"created": 0, "data": [{"url": payload["output"]}]}
```

要点：URL 由 `ctx.emit()` 指定、凭证由引擎按 `X-Auth-Emit` 注入，脚本从不接触凭证；  
`ctx.image_bytes()` 已能吃 URL / b64 / data-uri 三种入参，无需脚本自己分支下载。

## 9. 非功能性设计

### 9.1 性能

| 指标          | 目标         | 优化手段             |
| ----------- | ---------- | ---------------- |
| 单 Worker 并发 | 1000+ 等待连接 | asyncio 单线程事件循环  |
| 多 Worker 并发 | 4000+ 等待连接 | gunicorn 4 进程    |
| 脚本加载延迟      | < 100ms    | 模块级缓存 + 预加载      |
| 脚本执行延迟      | < 50ms     | 同进程函数调用，零序列化     |
| 图片下载延迟      | < 500ms    | Redis 缓存 5 分钟    |
| 端到端延迟（不含上游） | < 100ms    | 轻量 Gateway，无冗余处理 |

### 9.2 可用性

| 策略    | 实现                                                          |
| ----- | ----------------------------------------------------------- |
| 无状态设计 | 状态外置 Redis，Worker 可随时重启/扩容                                  |
| 健康检查  | `/health` 端点，返回 200 + 依赖状态                                  |
| 优雅关闭  | 收到 SIGTERM 后停止接受新请求，等待活跃请求完成                                |
| 超时熔断  | 分层预算（§3.3.1）：转换钩子 30s、单步 120s、编排总预算 300s、上游调用 60s、异步轮询 120s |
| 重试策略  | 上游 5xx 时指数退避重试 2 次（幂等请求）；级联中每级独立重试，重试耗时一并扣减总预算              |
| 级联降级  | `STAGE_FALLBACK` 声明的后处理级失败时返回上一级产物，标记 `degraded` 而非整单失败     |

### 9.3 安全

| 层级  | 措施                                                                     |
| --- | ---------------------------------------------------------------------- |
| 传输层 | TLS 1.3（Nginx 或 LB 终止）                                                 |
| 认证层 | 内部 Token 校验（与 New API 对接）                                              |
| 脚本层 | AST 扫描 + Import 白名单 + 分层超时熔断（Pillow 等能力经 `ctx` 门面暴露，不放宽 import 白名单）    |
| 级联层 | 各级 URL 只能取自 `X-Stage-Urls`（已过 SSRF 校验），凭证由引擎按 `X-Auth-Emit` 注入，不进脚本可见域 |
| 容器层 | 非 root、只读根文件系统、tmpfs、资源限制                                              |
| 网络层 | 容器间网络隔离，仅 Gateway 暴露端口                                                 |
