# 07 · ctx 基础能力分层：什么该进框架，什么不该

> 状态：**设计提案**（未实现、未改代码）。触发点见 §1。  
> 目标读者：适配器维护者 + 写新上游脚本的人。

---

## 1. 触发点：不是一个 bug，是一类 bug

`google/images@v1` 里的 `_tier()` 曾经这样写：

```python
allowed = [s for s in caps["sizes"] if order[s] <= order[want]]
return max(allowed or list(caps["sizes"]), key=order.get)   # 兜底取了"最大值"
```

请求 512、模型最低档是 1K 时，`allowed` 为空 → 兜底取到列表最大值 → **发出 4K**：尺寸不对，  
tokens 从 1120 翻到 2000。**它不报错，只是悄悄变贵、变样。**

这类逻辑（把"客户端要的"映射成"厂商支持的"）**每个图片上游脚本都要写一遍**，而每一遍都会遇到  
同样的边界：低于最低档、高于最高档、比例不在列表、模型带 `-preview` 后缀、某些模型固定分辨率。  
ARK 脚本有 `_ark_size()`，Google 脚本有 `_ratio()/_tier()`，下一个上游还会有第三份。

所以问题不是"缺一个函数"，而是：**同一种映射逻辑被反复重写，而它的失败方式是静默的**。

---

## 2. 判据：什么该进 ctx

四条硬标准，全部满足才进 ctx：

| # | 判据                                            | 反面（留下）                       |
| - | --------------------------------------------- | ---------------------------- |
| 1 | **厂商无关**：换一个上游，逻辑一个字不变                        | "3-pro 支持 1K/2K/4K" 是数据，不是逻辑 |
| 2 | **有唯一正确答案**：不需要业务判断                           | "要不要为了画质升档" 是策略              |
| 3 | **易错且失败静默**：写错不会当场报错                          | 纯拼字符串不会错                     |
| 4 | **要么是纯函数，要么需要 ctx 独占的资源**（infra / CPU / 线程跳转） | 脚本能安全自己做的，不搬                 |

补充一条**反判据**：**需要知道"渠道想要什么"的，一律不进**。ctx 不做策略决策。

---

## 3. 分类：用户列的能力，逐项判断

| 能力                        | 归属                         | 判据      | 说明                                      |
| ------------------------- | -------------------------- | ------- | --------------------------------------- |
| **比例兜底/转换**               | ✅ ctx 纯函数                  | 1,2,3,4 | 最近邻匹配是数学；"支持哪些比例"由脚本传入                  |
| **档位（清晰度/size）兜底/转换**     | ✅ ctx 纯函数                  | 1,2,3,4 | **本轮 bug 就在这里**；"档位表"是厂商数据              |
| **模型兜底/转换**               | ✅ ctx 纯函数（归一化）+ 脚本（别名表）    | 1,2,3   | 剥离 `-preview/-exp/-latest`、大小写归一 = 通用规则 |
| 图片元信息（宽高/mime/透明通道）       | ✅ ctx（只读 header，不解码）       | 2,3,4   | "保持输入比例"必须知道原图尺寸，现在只能整图解码               |
| **图片压缩**                  | ✅ ctx（CPU + 已有 Pillow 基建）  | 2,3,4   | `utils/imageops.py` 已有 to_thread 通道     |
| 参数替换的**上报出口**            | ❌ **不做**（见 §4.1 末）       | —       | 方向已安全、客户端可从返回图核对；`fit_tier` 已返回 `adjusted`，需要时再接 |
| 超分（upscale）               | ⚠️ 渠道编排（stages），**不进 ctx** | 1       | 它是"再调一个上游模型"，属于 `STAGES` 的职责            |
| 去水印                       | ❌ 明确不做                     | —       | 内容篡改 + 版权/合规风险，不是格式转换                   |
| 图生图的"保持人物一致"等语义           | ❌ 不做                       | 1       | 这是 prompt 工程，不是适配层能保证的                  |

## 4. 三条设计原则（比 API 更重要）

### 4.1 兜底必须回答"我改了什么"

```python
mapped = ctx.map_size("1024x1024", caps)
mapped.ratio, mapped.tier          # "1:1", "1K"
mapped.adjusted                    # True
mapped.notes                       # ["tier 512 -> 1K: below the model's floor"]
```

**静默兜底 = 静默改需求 + 静默改成本。** 本轮 4K 误判如果发生在生产，表现为"账单变贵、  
出图尺寸不对"，而日志里一片正常 —— 这正是项目一贯拒绝的失败方式（与"不静默丢图"同源）。  
`adjusted` 必须**被返回**（`fit_tier` 已经这么做了）；至于要不要再往客户端上报一份，见本节末尾。

**那么"上报出口"呢？—— 目前不做，而且早期那个 `ctx.note(text)` 是错的设计**

`adjusted` 已经在返回值里，但没有配一个上报出口。权衡下来不划算：

1. **方向已经安全**：`clamp` 只会往保守走（512 → 1K 是客户端要求的近似值），
   而真正危险的那种兜底（悄悄升到 4K）已经被规则本身排除掉了。
2. **客户端能自己核对**：返回的图**自带真实尺寸**。调用方想知道"你到底给了多大"，
   不需要我们再额外交付一份元数据。
3. **加响应头是公共契约变更**：成本落在每个调用方（要理解一个新 header），
   而收益只在"出问题时便于定位"—— 这件事日志与 trace 已经能做。
4. **早期的 `ctx.note(text)` 形态本身是错的**：名字泛（"note" 听起来像日志，实际语义很具体），
   更糟的是它把**自由文本**塞进响应头 —— 客户端拿到一串不可解析的字符串，等于没有契约。
   真要做，形态必须是结构化的：`adjusted(param, requested, used, reason)`。

**结论**：保持 `adjusted` 在返回值里（零成本），等出现真实需求（比如有调用方反馈"我不知道你改了尺寸"）
再接出口。真要接的时候形态是确定的，不需要重新设计。

### 4.2 兜底有方向，方向要显式

两种兜底，语义完全不同，API 上必须分开：

| 类型               | 何时用                           | 安全方向                              |
| ---------------- | ----------------------------- | --------------------------------- |
| **收敛（clamp）**    | 客户端要的档位/比例厂商不支持               | **往小/往保守走**，绝不上越                  |
| **升级（escalate）** | 厂商有**最低**要求（ARK 的 3686400 px） | 往上升，但**必须有上限**且必须 `adjusted=True` |

本轮的 bug 就是"该收敛时按升级处理了"。所以 `policy="clamp" | "escalate" | "strict"` 要显式传，  
默认 `clamp`；`strict` 表示宁可直接 `ctx.fail`（让调用方自己决定，而不是我们猜）。

### 4.3 逻辑进框架，数据留脚本

```python
CAPS = {                          # 脚本：厂商数据，实测校准
    "gemini-3.1-flash-image": {"tiers": ("512", "1K", "2K", "4K"), "wide": True},
    "gemini-2.5-flash-image": {"tiers": (), "wide": False},      # 固定分辨率
}
mapped = ctx.map_size(size, caps_of(model))     # ctx：算法
```

这样 `MODELS` 表的实测校准（本轮做过三轮）与算法解耦：**能力表改一行，所有脚本受益**。

## 5. API 草案（最小可用集合）

```text
# --- 已落地（adapter/ctxapi/mapping.py，纯函数，µs 级）------------------------
ctx.tier_value(tier)                          -> int | None      # "512"/"1k"/"1536px" -> 可比较数值
ctx.size_to_px(size)                          -> (w, h) | None   # 严格；坏值给 None 而不是替你猜
ctx.fit_tier(want, tiers, policy="clamp")     -> (tier, adjusted) # clamp 不越上限 / escalate 满足下限
ctx.fit_ratio(w, h, allowed)                  -> (w, h) | None   # 最近邻；平手取更方形
ctx.format_ratio(pair)                        -> "16:9" | None
ctx.is_extreme_ratio(pair, fold=4)            -> bool            # 由数值推导，不维护列表

# --- 还没做（P1）-----------------------------------------------------------
await ctx.image_info(ref)                     -> ImageInfo(w, h, mime, has_alpha)  # 只读 header
await ctx.compress_image(ref, *, max_bytes=None, max_edge=None,
                         fmt=None, quality=None) -> bytes          # 走 to_thread（imageops）
```

**早期草案里的两个"大函数"没有落地，这是有意的**：

- `ctx.map_size(size, caps)`（把比例 + 档位 + 说明打包返回）：两个真实用例的**输出形态不同** —— 
  Google 要 `ratio + tier` 两块，ARK 直接要一个预设字符串。硬塞进一个返回值，参数会爆炸，两边都不好用。
  **给两个零件让它们各自组合**更清楚。
- `ctx.resolve_model(name, aliases)`：职责被 `ctx.caps()` 吸收了 —— 解析别名/后缀本来就是为了查表，
  查完再回来自己解析一遍没有意义；`caps()` 直接返回 `{"model": 规范名, ...}`。

`ctx.note(text)` 已废弃 —— 名字太泛（像日志），更糟的是它把**自由文本**写进响应头（客户端无法解析）。
若将来真需要上报参数替换，形态应是结构化的（`adjusted(param, requested, used, reason)`），
由引擎汇总成响应头。**目前不做**，理由见 §4.1 末尾。

**教训**：草案里的"大函数"往往是想象的产物；写完两个真实消费者之后，正确的粒度才会显现 ——
这也是本轮把 `volcengine_ark` 读了一遍才发现它根本不需要这套东西（§6 实施记录）。

## 6. 优先级

| 级别     | 项                                                       | 理由                                               |
| ------ | ------------------------------------------------------- | ------------------------------------------------ |
| **P0** | `tier_value` / `size_to_px` / `fit_tier` / `fit_ratio` / `format_ratio` / `is_extreme_ratio` | ✅ **已落地**（§6 实施记录）：纯函数、零风险，直接消灭"每个脚本重写一遍 + 各踩一次 4K 坑"这类缺陷 |
| ❌ **不做** | 参数替换的上报出口（原 `ctx.note`） | 方向已安全 + 客户端可从返回图核对 + 加响应头是公共契约变更；`adjusted` 已在返回值里留着口子（§4.1） |
| **P1** | `image_info`                                            | "保持输入比例"目前只能整图解码；纯读 header 便宜一到两个数量级             |
| **P1** | `compress_image`                                        | 已有 Pillow + to_thread 基建，复用即可；压缩是"让请求能通过上游上限"的正解 |
| **P2** | `policy="escalate"/"strict"`                            | 目前只有 ARK 需要 escalate，需求还没到                       |

**建议的落地顺序**：P0 纯函数 → 把两个既有脚本（`volcengine_ark`、`google`）改成调用它 →  
用它们的现有测试证明行为不变（这是最硬的验收）。**框架能力只有在替换掉既有重复代码时才算真的成立**，  
否则只是多了一套没人用的 API。

> **实施记录（2026-09-11）**
>
> - ✅ 已抽出 `tier_value` / `size_to_px` / `fit_tier` / `fit_ratio` / `format_ratio` /

> - ⚠️ **`volcengine_ark` 未切换，而且不该切**：它的 `_ark_size()` 是三组枚举集合的查表  
>   （`SMALL`/`MID` → `"2k"`，`LARGE` → `"4k"`），既不是数学映射，也不发比例或多个档位 ——

## 7. 明确不做（防止 ctx 膨胀）

- **不做"自动选模型/自动降级到便宜模型"**：模型选择是控制面的商业决策，适配层猜不得。
- **不做"自动重试/降级重试"**：上游计费按次/按 token，重试 = 重复计费（项目既有结论）。
- **不做去水印**：合规问题，且与"格式转换"不是一类事。
- **不把厂商能力表搬进 ctx**：那是实测数据，会随上游改（本轮已改过三轮），放框架里会变成"需要发版才能更新的事实"。
- **不做"prompt 改写/翻译"**：属于调用方语义。

---

## 8. 验收

- 纯函数：单元测试覆盖边界（低于最低档 / 高于最高档 / 固定分辨率模型 / 空档位表 / 未知比例），  
  且**每个边界都要有"不得反向"的断言**（如 `fit_tier(512, ("1K","2K","4K")) == ("1K", True)`）。
- 替换既有脚本后：**现有测试全绿、行为不变**。实测结论：只有 `google` 有可抽的逻辑并已切换（19 项集成测试 + 38 项单测）；`volcengine_ark` 是枚举查表、不该切（§6 实施记录）。
- 上报出口：**未实现**（§4.1 决定不做）。将来若做，验收是"结构化字段 + 响应头受渠道开关控制"。

## 9. 上游 CDN 的 `Accept-Encoding` 缺陷（2026-09-11 实测，单变量定位）

同一张图 `https://s3ai.cn/cdn/20260901/53bbd0874ac247549beb8cb0226b5e66.jpg`：

| 请求                                                                      | 结果                                                               |
| ----------------------------------------------------------------------- | ---------------------------------------------------------------- |
| curl 默认（无 `Accept-Encoding`）                                            | **200**，6352993 bytes                                            |
| curl `--http1.1`                                                        | 200（**排除协议差异**）                                                  |
| curl + UA `Python/3.13 aiohttp/…` / `image-adapter/1.0` / `Mozilla/5.0` | 全 200（**排除 UA**）                                                 |
| curl + `Accept-Encoding: gzip, deflate`                                 | **404**                                                          |
| curl + `Accept-Encoding: gzip`                                          | **404**                                                          |
| curl + `Accept-Encoding: identity`                                      | **404**                                                          |
| aiohttp / urllib / urllib3 / requests                                   | **404**（它们默认都带这个头：aiohttp 是 `gzip, deflate`，urllib 是 `identity`） |

失败响应是 nginx 回的 S3 风格 XML：`<Code>NoSuchKey</Code>`，403 字节。

**结论**：该 CDN 对**任何显式声明 `Accept-Encoding` 的请求**返回 404（它同时返回  
`Vary: Accept-Encoding`，说明按该头做缓存分片 —— 极可能是分片后的某条链路没有这个对象）。  
与 HTTP 版本、UA、TLS 指纹都无关；**同一个 curl 只改这一个头就能复现**。

**对我们的影响与处置**：

- `ctx.download_image`（aiohttp）**下载这类 URL 会 404** → `image_ref_mode=inline` 会失败并报  
  `image_download_failed`（错误可读，不会静默）。
- **默认的 `auto` 模式把客户端 URL 直通给上游，不受影响** —— 这是"直通优先"的又一条实证理由  
  （前一条是零下载、零 base64 膨胀）。
- **不建议**为它给全局 aiohttp 会话去掉 `Accept-Encoding`（会失去自动解压，换一个更难查的故障），  
  更不该写进 ctx。遇到这类源就用渠道级 `image_ref_mode` 规避。

## 10. 图像处理能力层：格式转换 / 增强 / 擦除 / 水印 / 美颜

起因：腾讯云 MPS 把这类能力打包成一个接口（`ProcessImage`，v20190612）——  
**格式转换、图像增强（含 `SuperResolution` 超分）、图像擦除（`ImageEraseLogo` + 坐标框）、  
数字水印、美颜滤镜**。参考其形态后有两条结论。

### 10.1 先看这类能力的 IO 形态（决定了它们不该进 ctx）

| 特征 | 腾讯云 MPS 的实际形态                                                            | 对我们意味着                                                            |
| -- | ------------------------------------------------------------------------ | ----------------------------------------------------------------- |
| 输入 | `InputInfo.CosInputInfo{Bucket,Region,Object}` —— **对象存储**输入             | 需要先让图落到对方的存储里，或者对方能拉 URL                                          |
| 输出 | `OutputStorage`（不填则继承输入位置）—— **对象存储**输出                                  | 取回要下载，或把 COS 的 presigned URL 转给客户端                                |
| 返回 | **`TaskId`**，不是处理结果                                                      | **异步任务模型** —— 天然对应本项目的 `X-Async` + `poll_request`/`poll_response` |
| 限频 | 20 次/秒                                                                   | 需要退避与限流（与上游模型同一套考虑）                                               |
| 组织 | 还有模板 `Definition` 与编排 `ScheduleId`（30000 文字水印擦除 / 30010 图片扩展 / 30100 换装） | 同一个上游可以承载多个"能力"，用参数区分 —— 与我们的"一个脚本 + `X-Channel-Options`"一致       |

**结论：这类能力是"调用另一个上游服务"，与 `ctx` 的基础能力不是一个物种。**  
它们有网络、有计费、有异步、有失败率、有独立的凭据 —— 把它塞进 ctx 就等于把"外部依赖"  
伪装成"本地函数"，会污染 ctx 的语义（ctx 的价值恰恰是"脚本不碰基础设施"）。

### 10.2 三分法：本地同步 / 远端模型 / 纯决策

| 类别       | 典型能力                                | 归属                                               | 形态                                                                                  |
| -------- | ----------------------------------- | ------------------------------------------------ | ----------------------------------------------------------------------------------- |
| **本地同步** | 格式转换（png↔jpeg↔webp）、压缩、缩放、裁切、可见水印叠加 | **ctx**（`compress_image` + 已有 `imageops`/Pillow） | 同步、无外部依赖、零计费、`to_thread` 跳转                                                         |
| **远端模型** | 超分/增强、擦除（inpaint）、美颜、盲水印、换装、图片扩展    | **独立渠道 + `STAGES` 编排**                           | **同步语义（见 §14）**：优先选同步上游；只有返回 task id 的上游才用 `X-Async` 在适配器内轮询到完成。级联用 `STAGES`，**串行** |
| **纯决策**  | 选哪个模型、要不要增强、升不升档                    | **控制面**                                          | 不进适配层（§7 已列）                                                                        |

这一版把上一版的"超分 → 走 STAGES"讲清楚了：**它和"图生图"没有区别**，都是"发一个请求、  
拿一个结果"，只是算的东西不同。所以它复用的是**同一套**机制，不需要新概念：

```
STAGES = ["generate", "enhance", "upscale"]     # 生成 → 增强 → 超分，逐级可选
X-Stages: generate,upscale
X-Async:  poll=2,timeout=300                    # 远端能力多为异步任务
```

### 10.3 以腾讯云 MPS 为例的接入形态（不实现，仅列形状）

> **它是异步的（返回 `TaskId`）**，正好属于 §14 说的"异步只作兜底"那一类：若同一能力有同步供应商，  
> 优先接同步那家；接 MPS 就用 `X-Async` 把它**转成同步**，客户端依旧只发一次请求、只收一个结果。

```
X-Upstream-Url:   https://mps.tencentcloudapi.com
X-Upstream-Method: POST
X-Script-Ref:     tencent_mps/images@v1
X-Auth-Emit:      header:x-tc-... （TC3 签名走脚本 auth 相位）
X-Async:          poll=3,timeout=600
X-Channel-Options: {"cos":{"bucket":"...","region":"..."},"enhance":"super_resolution"}
```

脚本要做的事（与现有 Google 脚本同构）：request 相位构造 `ImageTask` → 拿到 `TaskId`；  
`poll_request`/`poll_response` 轮询任务状态；response 相位把它映射回 OpenAI 的 `data[]`。

**两个真正的工程难点**（比 ctx 能力重要得多）：

1. **存储桥**：MPS 只认 COS。若我方是 MinIO（s3ai.cn），就要么跨云上传一次，要么由调用方  
   直接给 COS 引用。这条成本必须显式暴露，不能藏在"一个参数"后面。
2. **取回**：输出在对方 COS 里，要么由我们下载后 re-host 到自己的桶（多一跳），要么把对方的  
   presigned URL 直接给客户端（**注意有效期与防盗链**，且客户端可能拉不动对方域）。  
   —— 这正是本项目 `temp_image_ttl` / `image_url()` 那套经验的复用点。

### 10.4 合规与可见性（设计约束，不是免责声明）

擦除 / 去水印 / 换装这类能力，**默认关闭**，且需要显式开启：

- 渠道级开关（`X-Channel-Options` 里显式声明），不做"客户端一句话就触发"。
- 每次调用记录**审计信息**：谁（控制面渠道）、什么时候、对哪张图、执行了什么能力。  
  项目已有 logfire span，加一个属性即可，不新建系统。
- 适配层不替业务做合规判断，但**必须让它可见、可审计、默认不生效** ——  
  一个"顺手就能去掉别人水印"的默认行为，迟早会变成事故。
- 数字水印还有另一半：**生成**（加可见/盲水印）是本地 Pillow 就能做的事，属于第一类；  
  **解析/检测**（SynthID 之类）是只读能力，可以进 ctx（无副作用），但不该默认开启。

## 11. 厂商能力表：从脚本里独立出去（✅ 已实施 2026-09-11）

> **实施记录**：`script_store/capabilities/google.json`（数据）+  
> `adapter/capabilities.py`（加载/缓存/覆盖）+ `adapter/ctxapi/caps.py`（`ctx.caps()`）
>
> - `tests/unit/test_capabilities.py`（24 项）。Google 脚本已切换，改表**不再需要动脚本文本**。  
>   加载器只认"有/没有事实"，**从不猜默认值**：表缺失或损坏时返回 `None`，脚本据此少发参数。  
>   表格另支持一个 `shared` 段：全家族共用的 `ratios` 之类只写一次，加载器合并进每个 model，  
>   脚本读到的是一个扁平 dict（`google.json` 已用它放 14 个比例）。

现状是硬编码在脚本里：

```text
MODELS = {
    "gemini-2.5-flash-image": {"sizes": (), "wide": False},
    "gemini-3.1-flash-image": {"sizes": ("512", "1K", "2K", "4K"), "wide": True},
    ...
}
```

**问题不是"放哪儿好看"，而是"改它要动代码"**：本轮为校准这张表改了 3 次脚本 —— 每次都要改脚本文本、  
重算 `manifest.json` 的 sha256、重新发版。而它本质上是**实测得到的事实**，不是逻辑。

**约束**：脚本在沙箱里不能 import adapter 模块（`ALLOWED_STDLIB` 白名单），所以能力表**必须经 ctx 注入**，  
不能被脚本直接读文件。

### 11.1 方案


```jsonc

    }
  }

```

脚本侧只剩一行：

```python

```

### 11.2 加载与覆盖

| 优先级   | 来源                                             | 场景                             |
| ----- | ---------------------------------------------- | ------------------------------ |
| 1（最高） | `X-Channel-Options.caps`                       | 单渠道临时校准，不改文件                   |
| 2     | `SCRIPT_OVERLAY_DIRS` 下的 `capabilities/*.json` | 生产热更新（挂载卷），**复用现有 overlay 机制** |
| 3     | `script_store/capabilities/*.json`             | 随镜像发布的权威值                      |

引擎侧：加载 + 按 `(mtime, size)` 缓存（与 `DirStore` 同一手法，不新造缓存）、文件损坏则降级为  
"无能力表"（脚本回落到自己的默认值，与 `manifest.json` 的容错策略一致）。

### 11.3 收益（对照本轮的实际代价）

| 本轮的动作                        | 现在                                         | 独立之后                                                |
| ---------------------------- | ------------------------------------------ | --------------------------------------------------- |
| 校准 `tiers` / 加 `-preview` 后缀 | 改脚本 → 重算 digest → 改 manifest → 重跑测试 → 重新发版 | 改一个 JSON（或挂 overlay），**不动代码、不动 digest**             |
| 第二个上游复用同一份事实                 | 各脚本各抄一份，各自漂移                               | 一份权威表，多脚本共享                                         |
| 记录"这行数据是怎么来的"                | 只能写在注释里                                    | `verified_at` / `verified_against` 是结构字段，可被实测脚本自动回填 |

**注意边界**：独立出来的是**数据**，不是逻辑。`map_size`/`fit_tier` 仍然进 ctx（§5），  
上游的"特有语义"仍然留在脚本里（例如"这个字段名要用 camelCase"这类硬事实）。

## 13. 这些能力也要走 `/v1/images`：它们就是独立的"模型"

用户的补充：**格式转换 / 增强 / 擦除 / 水印 / 美颜这些能力，以后也要能被 `/v1/images/*` 调用  
—— 它们本身就是单独的 AI 模型/能力**。这条对架构是个好消息，因为它几乎不需要新东西。

### 13.1 为什么现在就已经成立

`/v1/images/*` 从来不是"生成图"的端点，而&#x662F;**"把 OpenAI images 请求翻译成某个上游请求"**&#x7684;端点，  
它不知道、也不需要知道上游在算生成还是算超分。逐个对照现有机制：

| 需求                      | 现有机制                                                 | 是否够用                      |
| ----------------------- | ---------------------------------------------------- | ------------------------- |
| 客户端用 `model` 指定能力       | 控制面按 model 选渠道 → `X-Upstream-Url` + `X-Script-Ref`   | ✅ 适配器**不持有模型注册表**，这正是设计意图 |
| 单图进、单图出                 | `image` 三态（URL / data URI / 裸 b64）                   | ✅                         |
| 不需要 prompt 的能力          | `validate_images_body`：**有 `image` 时 prompt 可选**     | ✅ 已经是这么写的                 |
| 需要 mask 的能力             | `mask` 字段（JSON 与 `/v1/images/edits` 的 multipart 均支持） | ✅ 引擎已有，脚本决定是否透传/报错        |
| 厂商专有参数（坐标框、强度、模板 ID）    | body 是 **superset**，未知字段原样保留给脚本                      | ✅ 透传即可，不必改契约              |
| 异步任务（MPS 这类返回 `TaskId`） | `X-Async: poll=…` + `poll_request`/`poll_response`   | ✅                         |
| 失败可表达                   | `ctx.fail(...)`                                      | ✅                         |
| 输出 url / b64 两态         | `response_format` + `ctx.upload_temp_image`          | ✅                         |

**所以"新增一个能力"= 控制面配一个渠道 + 一份能力表数据 + 一个脚本**，不需要新端点、不需要在  
adapter 里加"能力类型"分支。**adapter 里一旦出现 `if capability == ...`，就是这层设计被破坏了。**

### 13.2 每类能力与 OpenAI 字段的对应（写进文档给客户端看）

| 能力        | `prompt` | `image` | `mask` / 厂商扩展           | `size`  | `n` | 说明                      |
| --------- | -------- | ------- | ----------------------- | ------- | --- | ----------------------- |
| 格式转换      | 忽略       | 必填      | —                       | 可选（兼缩放） | 1   | 本地可做，也可走远端              |
| 图像增强 / 超分 | 可选（强度）   | 必填      | 厂商字段（如 `EnhanceConfig`） | 目标档位    | 1   | 远端模型                    |
| 图像擦除      | 可选（擦什么）  | 必填      | **`mask` 或坐标框**（厂商字段）   | 保持      | 1   | 坐标框 OpenAI 没有 → 走厂商扩展透传 |
| 数字水印（生成）  | 可选（文字）   | 必填      | 厂商字段（位置/透明度）            | 保持      | 1   | 本地 Pillow 可做            |
| 美颜滤镜      | 可选（强度）   | 必填      | 厂商字段                    | 保持      | 1   | 远端模型                    |

两个**契约缺口**要显式处理，别让客户端猜：

1. **擦除的坐标框**：OpenAI 契约里没有"框"的概念。两条路 —— ① 厂商扩展字段透传（`body` superset 已支持，  
   文档写清字段名）；② 让客户端用 `mask`（我们已有该字段与 multipart 通道）。**默认走 ①，② 作为兼容**。
2. **强度类参数**（美颜/增强级别）：同样走厂商扩展，**不要**自作聪明映射到 `quality`。

### 13.3 能力表要多承载一个维度：这个能力**接受哪些字段**

既然"能力"和"生成"在适配层同形，差异就落在**数据**里。所以 §11 的 `capabilities/*.json` 再加一段声明：

```jsonc
{
  "models": {
    "image-enhance": {
      "kind": "enhance",                       // generate|format|enhance|erase|watermark|beauty
      "requires": ["image"],
      "accepts":  ["size", "enhance_config"],
      "ignores":  ["n", "quality", "prompt"],
      "async": true
    }
  }
}
```

脚本据此在 **request 相位前置校验**：客户端给了被忽略/不支持的字段时，**给明确的 400**  
（`param` 指到具体字段），而不是把错误推给上游、让客户端看到一句读不懂的厂商报错。  
这与既有行为一致 —— Google 脚本对 `n>1` 和 `mask` 就是这么做的。

### 13.4 明确不做（保持这层干净）

- **不做模型/能力路由**：`model` → 渠道的映射在控制面。适配器拿到什么就发什么。
- **不维护能力清单接口**（`GET /v1/models` 之类）：那是控制面的账，适配器没有注册表。
- **不做能力编排**：先增强再超分这类链路，由控制面拆成多次调用，或用 `X-Stages` 级联；  
  适配器不发明"工作流引擎"。
- **不做合规判断**：擦除/美颜这类能力作为独立模型暴露时，**谁可以用**由控制面权限决定；  
  适配器只保证"默认关闭 + 每次调用可审计"（§10.4）。

### 13.5 落地清单（新能力 = 三件事）

1. `script_store/<vendor>/images@v1.py` —— 把 OpenAI 请求翻译成该能力的上游请求（含 `ctx.fail` 出口）；
2. `script_store/capabilities/<vendor>.json` —— 该能力的 `kind/requires/accepts/ignores`（§11、§13.3）；
3. 控制面配渠道：`X-Upstream-Url` + `X-Script-Ref` + 凭据 + `X-Async`（**仅当上游只支持异步任务时**，见 §14），  
   并**用 `tools/` 下的探针脚本对真实上游跑一遍**再上线（照 §9 的做法）。

前两件随镜像发布，第三件在控制面 —— **这条边界本身就是这个架构最值钱的部分：加能力不需要改框架。**

## 14. 同步优先：异步只是兜底，编排不做异步

用户的判断（2026-09-11）：**能力层级大部分是同步接口，把异步放进编排太复杂**。这条要写死成原则，  
因为它决定了整层的形状。

### 14.1 客户端看到的永远是"一个请求 → 一个结果"

`X-Async` 这个机制的名字容易误导：它**不是**给客户端提供异步能力，而是**把异步上游转成同步**——  
客户端仍然只发一次请求、只收一个结果，适配器在内部轮询到任务完成。所以：

| 形态                        | 是否对外暴露   | 说明                                                                           |
| ------------------------- | -------- | ---------------------------------------------------------------------------- |
| 同步上游（一次调用出结果）             | ✅ 默认     | **能力层优先选这类**：格式转换、压缩、多数增强/美颜服务都有同步接口                                         |
| 异步上游（返回 task id）          | ⚠️ 仅兜底   | 用 `X-Async` + `poll_request`/`poll_response` **在适配器内轮询到完成**，客户端无感（MPS 就是这一类） |
| 客户端可见的异步（提交任务 → 查任务 → 回调） | ❌ **不做** | 会引入状态、幂等、回调、过期清理，且控制面已经有自己的任务语义，适配层不该再发明一套                                   |

明确不做的东西：`GET /v1/images/tasks/{id}` 这类查询接口、webhook 回调、`status` 轮询字段。  
**只要客户端还能只发一次请求就拿到图，异步就只是实现细节。**

### 14.2 编排 = 串行同步，不做并发/不做 DAG

多能力串联（例如 擦除 → 增强 → 超分）统一走**串行**：

```
STAGES = ["erase", "enhance", "upscale"]      # 顺序执行，前一级产物喂给下一级
X-Stages: erase,enhance
X-Stage-Timeout: total=300                    # 总预算，已有机制
```

理由（按重要性排序）：

1. **可预测**：延迟是各级之和，能算、能估、能对客户端解释；并发编排的延迟取决于最慢的一级，  
   但失败组合爆炸。
2. **成本可控**：串行下一级失败就是整体失败，不会出现"局部成功、部分计费"的账单争议。
3. **降级简单**：`STAGE_FALLBACK` 已经能表达"后处理级失败就返回上一级产物"——  
   并发编排要让这个语义成立，得引入事务/补偿，代价远大于收益。
4. **与既有实现一致**：`stages.py` 本来就是严格串行（`_run_stage` 逐个 await）。

**因此本项目那条"未做项"——`ctx.gather()`（单请求并发多上游）——优先级正式下调**：它不是"待补的能力"，  
而是**被刻意排除的设计**。真需要并发，说明该由控制面拆成多个请求去做（它才有重试与额度语义）。

#### 14.2.1 排除到哪里为止：并发生成调用 ❌ / 并发素材物化 ✅

上面那条排除有个容易误伤的范围，这里划清楚。**被排除的是"一次请求内并发发起多个上游生成
调用"**（`ctx.gather()` 的本义：`n>1` 扇出、多级并行、DAG）。**不属于**排除范围的是
**素材物化（materialization）**——把一次请求已经在手上的 N 个素材搬进来或搬出去：

| 动作 | 例子 | 属于被排除的"编排"吗 |
| --- | --- | --- |
| 读入站素材 | N 张客户端图片的下载 / base64 解码 | ❌ 不是 |
| 取出站产物 | 上游已返回的 N 个 `data[]` 逐项取回、落存储 | ❌ 不是 |
| 写素材 | N 张图的 `upload_temp_image`（re-host、`response_format=url`） | ❌ 不是 |
| **并发生成调用** | `n>1` 扇出、多级并行、DAG | ✅ **是，仍然排除** |

判据是机械的三条，**缺一不可**：

1. **不产生额外的上游生成调用**。并发的是客户端的入站素材，或**已经计过费**的产物搬运
   —— 上游调用次数与计费口径（`n × len(STAGES)`）都不因并发改变。
2. **失败语义不变**。仍是"任一子任务失败即整体失败"，错误码与串行时逐个一致。
   这一条把并发化限定在**本来就 fail-fast 的路径**上，不引入"局部成功、部分计费"。
3. **并发度有上限**。受 `fanout_concurrency`（默认 3）约束；
   注意它**不是** `docs/04_Spec.md` AC-30 里那个给"`n` 次上游调用"用的 `concurrency`，
   两者服务的是不同对象，别合并成一个配置项。

#### 14.2.2 承载点：`ctx.fanout`（✅ 已实施 2026-09-12）

脚本**自己拿不到并发**：`sandbox.ALLOWED_STDLIB` 是纯 stdlib 白名单且排除 `asyncio`，
`adapter.*` 内部也不可导入（实测 `import asyncio` / `concurrent.futures` / `anyio` / `httpx`
全部 `Forbidden import`）。所以并发物化只能由框架借出这一个入口：

```python
results = await ctx.fanout(items, work)      # work: async (item) -> value
```

- **保序**：`results[i]` 属于 `items[i]`，与完成顺序无关。
- **限量**：同时在飞不超过 `fanout_concurrency`。
- **失败语义不变**：按**输入顺序**重抛最早的失败并保留其类型 ⇒ 脚本 `ctx.fail()` 的 400 仍是 400。
  ⚠️ 不能用 `asyncio.TaskGroup`：它把子任务的异常包进 `ExceptionGroup`，而 `_call_phase` 的
  `except AdapterError` 匹配不到 ⇒ **400 变 500**（实测）。这就是必须用
  `gather(return_exceptions=True)` 的原因。
- `work` **允许闭包**（可捕获 `ctx` 与局部量）—— 否则"先下载再 re-host"这类两步操作无法表达。
- **空列表不调用任何东西；单项走串行路径** ⇒ N=1 与旧行为逐字节相同。

实现：`adapter/utils/fanout.py`（原语）+ `adapter/ctxapi/fanout.py`（门面）。
8 项单测，并做过**变异自证**：退回串行 / 去掉上限 / 按完成序收集，三种错法都会报红。
首个消费者是 `openai/images@v2`（**`v1` 原样不动**，`latest` 前移到 v2、`stable` 留在 v1）。

**§14.2 的结论不变**：不做并发生成调用、不做 DAG、`stages.py` 级联仍严格串行、
`ctx.gather()` 仍是"被刻意排除的设计"。本节只是把**排除到哪里为止**写出来，
免得下一个人把"不并发"读成"连 N 张图的输入都不能一起取"。

两条实现约束（实测得出，写在这里免得重踩）：

- **禁止用 `asyncio.TaskGroup` 做扇出**。它会把脚本 `ctx.fail()` 抛出的 `AdapterError` 包进
  `ExceptionGroup`，而 `executor._call_phase` 的 `except AdapterError` 匹配不到 → 落到
  `except Exception` → `ScriptRuntimeError` → **该报 400 的变成 500**。并且脚本侧无法用
  `except*` 解包（`_call_phase` 在引擎里，不在脚本沙箱内）。必须用
  `asyncio.gather(..., return_exceptions=True)` 再手动挑出首个 `AdapterError` 重抛。
- **有共享可变状态的循环不能直接并发**。`google/images@v1` 的 `inline_total_max_bytes` 额度单元
  （`allowance`）是"读后写"，且写入点都在 `await` 之后；直接并发会让**哪张图被 inline 变成
  非确定行为**，护栏失效。这类只能拆成**两阶段**：并发阶段只做 I/O，额度分配仍按输入顺序串行。

> 顺带纠正一处措辞：`script_store/openai/images@v1.py` 里那句
> "The adapter never fans out to several upstream calls" 把"下载产物"和"调用上游"当成了同一件事。
> 该处串行的真实理由是它属于**素材物化**而当时没有并发设施，不是它"像上游调用"。

### 14.3 代价与边界（诚实说清楚）

- **延迟叠加**是串行的固有代价。缓解手段是**总预算控制**（`X-Stage-Timeout` 的 cascade budget）  
  与**尽早降级**，而不是加并发。唯一的例外是 §14.2.1 的素材物化：那里的并发压的是*等待*，
  不是编排；但它也**不改变各级延迟相加**这条算式，只是把同一级内的 N 次 I/O 折叠成一次等待。
- **素材物化的并发只压缩 I/O 等待，压不动 CPU**：`binascii` **不释放 GIL**（实测见 `docs/06`），
  base64 编解码仍然串行占着 event loop，因此收益上限 ≈ **(N−1)/N × 网络等待时长**
  ——低 RTT 同域时接近零，跨境大图时才明显。**先测收益再动手**，别把"加上 `gather`"当成优化。
- **后端差异决定并发是否真有效**：fal 侧是一次 `await client.upload(...)`（`FalStore.put`），
  实测一次 1603ms 的 `put` 期间事件循环 tick 了 139 次 ⇒ **未阻塞**；4 路并发 `put` wall 6198ms
  vs 串行 10719ms（比值 0.58）。minio-py 是**同步库**，`MinioStore.put` 走 `asyncio.to_thread`，
  并发有效但占用默认线程池 `min(32, cpu+4)`。**存储后端不是"上游"**，两者都不受
  `HTTP_POOL_LIMIT_PER_HOST` 约束——那个池只管 `ctx.http`。这两组数字来自本地报告
  `reports/2026-09-11_fal-object-storage/`（**该目录未入库**，所以结论写在这里）。
- 上游只支持异步时，**转同步会占用一个 worker 连接最长 `poll timeout`**。所以：
  - 异步上游的 `poll` 间隔别太小（默认 2~3s 足够），`timeout` 要显式给（默认 300s 可能不够）；
  - 这类渠道的并发上限要按"单请求占用时长"折算，而 `HTTP_POOL_LIMIT_PER_HOST` 是 per-worker 的资源上限，  
    **不是节流阀**（既有结论）。
- 超时的表现要可区分：`poll_timeout`（上游一直没完成）与 `stage_timeout`（某一级超预算）是两个码，  
  不要合并成一个 504。

### 14.4 对能力表的影响

编排字段因此收敛为"顺序 + 预算 + 降级"，不需要图结构：

```jsonc
"image-erase": {
  "kind": "erase",
  "requires": ["image"],          // 上游链路的入口条件
  "outputs": ["image"],           // 下一级能接什么
  "async": false,                 // 优先同步；true 只表示"要转同步"
  "fallback": "skip"              // 失败时跳过本级（而不是回滚整条链）
}
```

`async: true` 的含义是"**这个实现需要内部轮询**"，而不是"这个能力是异步的" —— 前者是实现细节，  
后者是契约泄漏。这条区分值得写进注释，否则下一个人很容易把它当成对外语义又加回异步接口。

## 15. 能力清单：从产品 UI 反推的分类与统一参数模型

用户提供了产品里的能力入口截图（一排按钮）：**变清晰、消除、抠图、扩图、局部替换、文字替换、  
图片修复、换风格、AI重绘、相似图、提线稿**。这批能力正好检验前面所有分层规则。

### 15.1 它们的共性：都是"单图进、单图出"，差别只在**需要什么额外输入**

| 额外输入            | 能力                                           |
| --------------- | -------------------------------------------- |
| 无               | 变清晰、抠图、提线稿                                   |
| **区域**（mask 或框） | 消除、局部替换、图片修复（有时）                             |
| **文本**          | 文字替换（把 A 换成 B）                               |
| **枚举/数值**       | 换风格（style）、扩图（方向 + 幅度）、变清晰（倍数/目标尺寸）、AI重绘（强度） |
| **语义 prompt**   | 局部替换、AI重绘                                    |

所以真正的抽象不是"能力名"，而是 **变换算子 + 它接受的参数**。


### 15.2 统一参数命名空间（这一节是本节的重点）

OpenAI 的 images 契约只有 `image` / `mask` / `prompt` / `size` / `n` / `quality` / `response_format`。  
上面那批能力需要的参数远超它。如果每个能力各造一套字段（`erase_area` / `replace_region` / `text_from` /  
`style_name` / `expand_direction` …），客户端与控制面会被字段名淹掉，**换一个上游还要重学一遍**。

建议：**一个命名空间，由能力表声明谁用哪些**。

```jsonc
"x-capability": {
  "region":    [[x1, y1, x2, y2]],            // 区域类，支持多块
  "text":      {"from": "¥199", "to": "¥99"}, // 文字替换
  "style":     "anime",                       // 换风格
  "scale":     2.0,                           // 超分倍数（与 long_side 二选一）
  "long_side": 1920,                          // 目标长边
  "direction": "top,bottom",                  // 扩图方向
  "strength":  0.6                            // 重绘强度
}
```

四条规则：

1. **官方字段优先**：区域优先用 OpenAI 原生的 `mask`（`/v1/images/edits` 的 multipart 已经支持），  
   `x-capability.region` 只补"框"这一形态（mask 表达不了矩形集合，而不少上游按框处理/按框计费）。
2. **其余参数统一放 `x-capability`**，不散落到 body 顶层 —— 落一层就有归属，客户端只学一套。
3. **能力表声明**（§13.3 的 `accepts` + 新增 `params`）：脚本据此做**前置 400，param 精确到  
   `x-capability.text.from` 这种粒度**。客户端不该看到上游的一串方言错误。
4. **不猜默认**：缺省就用上游默认（如 MPS 的 `Percent` 默认 2.0），**不要我们自己编一个倍数**。


### 15.3 逐个归类

| UI 能力 | 额外输入                  | 归属                | 已知上游对应 / 说明                                                                 |
| ----- | --------------------- | ----------------- | --------------------------------------------------------------------------- |
| 变清晰   | 倍数 / 目标尺寸             | **远端模型**（超分）      | MPS `AdvancedSuperResolutionConfig`，已在 `docs/08` 方案化                        |
| 提线稿   | 阈值                    | **本地同步**          | 纯像素运算（边缘检测），无需模型 → 与"格式转换/缩放/压缩"同类                                          |
| 抠图    | 无（可选羽化）               | **远端优先**          | ⚠️ 修正 §10.2 的判断：抠图要**分割模型**（体积大、迭代快），放 ctx 意味着引擎带模型文件与更新节奏 —— 不值得。本地只做纯像素运算 |
| 消除    | `region` 或 `mask`     | **远端模型**（inpaint） | 上游 `EraseConfig`；MPS `ScheduleId 30000` 是"文字水印擦除"这个**场景**                   |
| 局部替换  | `region` + prompt     | **远端模型**          | 语义由 prompt 携带，区域由框/mask 携带                                                  |
| 文字替换  | `text{from,to}`（区域可选） | **远端 + 场景编排**     | 需要 OCR 定位 → 本质是"擦除 → 重绘"两级；MPS 用 `ScheduleId 30000` 表达                      |
| 图片修复  | 可选 `region`           | **远端模型**          | 老照片修复（去噪 + 人脸修复），多为独立模型                                                     |
| 换风格   | `style` 或参考图          | **远端模型**          | style transfer；也可能是生成模型的 img2img + 风格 prompt                                |
| AI重绘  | prompt + `strength`   | **就是图生图**，已有渠道类型  | **不必新增分类** —— 它是生成，不是"新能力"                                                  |
| 相似图   | 数量 / 参考               | ⚠️ **需澄清语义**      | 若是"**以图搜图**" → **检索能力，不属于本适配层**（另一个产品）；若是"生成相似图" → 生成能力                     |
| 扩图    | `direction` + 幅度      | **远端模型**          | MPS `ScheduleId 30010`（图片扩展）= outpainting                                   |

两个结论值得单独记：

- **"AI重绘"不是新能力**，它是图生图；**"提线稿"不是 AI 能力**，它是本地像素运算。  
  一批 UI 按钮里，真正的"新上游"往往只有一半 —— 归类清楚了才知道要接几个渠道。
- **"相似图"必须先澄清语义**：以图搜图属于检索，硬塞进图像适配层会引入一整套完全不相关的东西。

### 15.4 一个产业事实：上游自己就在做编排

上面有两个能力（**文字替换**、**扩图**）在上游是**场景**而不是算子 —— MPS 的  
`ScheduleId`：`30000 文字水印擦除` / `30010 图片扩展` / `30100 换装`。名字叫"场景"，  
意味着**上游内部已经编好了那条管线**，我们只需要传一个 ID。

这给 §14 的编排策略补上优先级（**能借上游的就别自己编**）：

| 优先级 | 做法                                               | 何时用                       |
| --- | ------------------------------------------------ | ------------------------- |
| 1   | **上游的场景参数**（`ScheduleId` / `Definition` / 模板 ID） | 上游有对应场景 —— 省事、质量对齐、计费口径清晰 |
| 2   | 我们自己的 `STAGES` 串行（§14.2）                         | 上游只有单算子，而业务需要两级           |
| 3   | 控制面拆成多次调用                                        | 跨厂商组合（适配层不承担）             |

**`STAGES` 是兜底，不是首选。** 自己编一条管线要自己承担每一级的失败与计费语义，  
而上游的场景编排已经在它那边调好了。

### 15.5 能力表因此要加两个字段

```jsonc
"image-erase": {
  "kind": "erase",
  "requires": ["image"],
  "params": ["region", "mask", "prompt"],     // 新增：接受哪些 x-capability 参数
  "outputs": ["image"],
  "async": false,
  "upstream": {"scene": 30000}                // 新增：这个能力在上游是"场景"而非"算子"
}
```

`params` 让脚本能做精确到参数名的 400；`upstream.scene` 记下"它是场景"这个事实，  
免得下一个人拿着算子契约去调场景接口。

### 15.6 不做的

- **不做以图搜图 / 相似图检索**：它不是图像变换，是检索，属于另一个产品。
- **不做"一键美颜/一键漫画"这类组合营销能力**：那是"换风格 + 图片修复 + …"的产品侧封装，  
  我们只暴露算子与上游场景，组合交给调用方。
- **不做"自动判断该用哪个能力"**：模型/能力选择在控制面（§7 已列）。
